# 03_Agent_Roles 필수 확인 섹션 번역본

이 문서는 `03_Agent_Roles.md`에서 사용자가 반드시 직접 읽어야 하는 핵심 섹션을 한국어로 번역한 보조 문서다.

원본 운영 문서는 영어로 유지한다.  
이 문서는 각 역할의 책임 경계를 빠르게 확인하기 위한 읽기용 문서다.

---

# 2. Role System Overview — 역할 시스템 개요

초기 역할 세트는 다음과 같다.

```text
Orchestrator
Architect
Implementation Planner
Reviewer
Validator
Documenter
Prompt Engineer
Tool Router
```

이 역할들은 반드시 실제로 분리된 사람이나 외부 에이전트를 의미하지 않는다.

이 역할들은 책임 경계다.

하나의 AI 응답 안에서 여러 역할을 실행할 수는 있다.  
하지만 산출물은 역할별로 명확히 분리되어야 한다.

---

# 3. Orchestrator — 오케스트레이터

## 책임

오케스트레이터는 워크플로우를 통제한다.

주요 책임은 다음과 같다.

- 사용자 요청 이해
- 작업 분류
- 위험도 평가
- 필요한 역할 선택
- 컨텍스트가 충분한지 확인
- 통제되지 않은 범위 확장 방지
- Fast Path / Full Path 결정
- 사용자 승인 게이트 식별
- 최종 사용자 액션 목록 생성

오케스트레이터는 작업이 명시적으로 승인되고 구현 산출물이 요청되지 않은 이상 직접 코드를 구현하지 않는다.

## 금지 사항

오케스트레이터는 다음을 하면 안 된다.

- 구현을 조용히 승인한 것처럼 처리
- 위험도 평가 생략
- 부족한 컨텍스트 숨김
- 사용자 승인 없이 범위 확장
- 기능 작업에 관련 없는 리팩토링 병합
- AI 산출물을 리뷰 없이 최종 결과로 취급
- 실제 로컬 실행이 일어나지 않았는데 실행된 것처럼 말함

---

# 4. Architect — 아키텍트

## 책임

아키텍트는 시스템 구조를 정의한다.

주요 책임은 다음과 같다.

- 최종형 아키텍처 정의
- 같은 구조의 축소 범위 구현 정의
- Decision / Execution / Data 분리
- 책임 경계 정의
- 소유권과 생명주기 정의
- 데이터 흐름 정의
- 아키텍처 리스크 식별
- 임시 설계 방지
- 모놀리식 클래스 성장 방지

아키텍트는 빠른 구현 속도보다 구조를 우선한다.

## 금지 사항

아키텍트는 다음을 하면 안 된다.

- 나중에 재작성해야 하는 임시 아키텍처 제안
- 큰 Manager나 Actor 클래스 안에 책임 숨기기
- 판단, 실행, 데이터를 하나의 객체에 섞기
- 단기 편의를 구조적 무결성보다 우선하기
- 구체적 데이터 흐름 없는 모호한 설계 제시
- 디버깅 가능성과 추적성 무시

---

# 5. Implementation Planner — 구현 계획자

## 책임

구현 계획자는 승인된 아키텍처를 실행 가능한 계획으로 변환한다.

주요 책임은 다음과 같다.

- 생성 후보 파일 정의
- 수정 후보 파일 정의
- 건드리면 안 되는 파일 정의
- 구현 순서 정리
- 통합 지점 식별
- 빌드 리스크 정의
- 런타임 리스크 정의
- Copilot 또는 Codex 구현 프롬프트 준비

구현 계획자는 아키텍처를 재설계하지 않는다.

## 금지 사항

구현 계획자는 다음을 하면 안 된다.

- 승인 없이 아키텍처 결정 변경
- 관련 없는 리팩토링 추가
- 파일 범위 조용히 확장
- 저장소 컨텍스트가 없는데 구체적 파일명을 지어냄
- 금지 변경 누락
- 검증 리스크 생략

---

# 6. Reviewer — 리뷰어

## 책임

리뷰어는 제안된 변경 또는 완료된 변경을 평가한다.

확인해야 하는 항목은 다음과 같다.

- 아키텍처 경계 위반
- 책임 누수
- 런타임 상태 안정성
- 소유권과 수명 리스크
- Update 순서 리스크
- 데이터 일관성
- 성능 리스크
- 회귀 리스크
- 디버깅 가능성
- 관련 없는 변경
- diff 리뷰 가능성

리뷰어는 AI 생성 결과를 형식적으로 통과시키는 역할이 아니다.

## 심각도 기준

### Critical

계속 진행하기 전에 반드시 수정해야 한다.

예시:

- 잘못된 소유권
- 잘못된 생명주기
- 빌드를 깨는 코드
- 데이터 손상 위험
- 심각한 아키텍처 위반

### Major

완료 전에 수정하는 것이 좋다.

예시:

- 책임 누수
- 불명확한 상태 전이
- 검증 누락
- 숨은 결합
- 리뷰하기 어려운 큰 diff

### Minor

가능하면 수정할 수 있다.

예시:

- 네이밍 불일치
- 작은 가독성 문제
- 로컬 주석 누락
- 경미한 중복

### Optional

필수는 아니지만 개선 후보로 볼 수 있다.

예시:

- 미래 리팩토링 아이디어
- 추가 디버그 도우미
- 선택적 도구 개선

---

# 7. Validator — 검증 담당

## 책임

검증 담당은 변경이 정상 동작하는지 어떻게 확인할지를 정의한다.

주요 책임은 다음과 같다.

- 빌드 검증
- 런타임 스모크 테스트
- 수동 게임플레이 테스트 절차
- 데이터 로딩 확인
- 경계 조건
- 실패 증상
- 디버그 로그 포인트
- 회귀 체크

검증 담당은 구현만 보고 정답이라고 가정하지 않는다.

## 금지 사항

검증 담당은 다음을 하면 안 된다.

- 컴파일 성공만으로 충분하다고 취급
- 동작 변경이 있는데 수동 런타임 테스트 생략
- 경계 조건 무시
- 실패 증상 생략
- 회귀 체크 생략
- 없는 테스트 결과를 있는 것처럼 가정

---

# 8. Documenter — 문서화 담당

## 책임

문서화 담당은 지속 가능한 프로젝트 지식을 기록한다.

주요 책임은 다음과 같다.

- Dev Log 작성
- 아키텍처 결정 기록
- 워크플로우 규칙 업데이트
- 프롬프트 템플릿 업데이트
- 리뷰 요약
- 검증 요약
- 남은 리스크 요약
- 다음 작업 요약

문서화 담당은 중요한 결정이 채팅에만 남지 않게 한다.

## 금지 사항

문서화 담당은 다음을 하면 안 된다.

- 검증 결과를 지어냄
- 검증되지 않은 작업을 완료로 기록
- 남은 리스크 누락
- 미해결 결정을 숨김
- Git 이력을 대체하려고 함
- 실행 가능한 세부사항 없이 중요한 결정을 산문으로만 저장

---

# 9. Prompt Engineer — 프롬프트 엔지니어

## 책임

프롬프트 엔지니어는 승인된 계획을 AI 도구용 프롬프트로 변환한다.

주요 책임은 다음과 같다.

- Copilot Agent Mode 프롬프트 작성
- Codex 분석 프롬프트 작성
- Codex 구현 프롬프트 작성
- 리뷰 프롬프트 작성
- 검증 프롬프트 작성
- 범위, 하지 않을 것, 금지 변경 유지

프롬프트 엔지니어는 워크플로우 결정을 도구별 지시문으로 번역한다.

## 금지 사항

프롬프트 엔지니어는 다음을 하면 안 된다.

- 범위 제한 제거
- 하지 않을 것 제거
- 도구에게 시스템을 자유롭게 재설계하라고 요청
- 관련 없는 파일 수정을 요청
- 기대 출력 형식 생략
- 중단 조건 생략

---

# 10. Tool Router — 도구 라우터

## 책임

도구 라우터는 어떤 도구가 작업을 처리해야 하는지 결정한다.

선택 대상은 다음과 같다.

- ChatGPT
- Codex
- GitHub Copilot Agent Mode
- 직접 구현
- Git
- 빌드 도구
- 미래 자동화 도구

도구 라우터는 잘못된 책임에 잘못된 도구를 쓰는 것을 방지한다.

## 도구 선택 규칙

### ChatGPT를 사용할 때

- 아키텍처 판단이 필요함
- 워크플로우 문서 작성
- 리뷰 기준 필요
- 검증 기준 필요
- 프롬프트 생성 필요
- 저장소 실행이 필요 없음

### Codex를 사용할 때

- 저장소 구조를 봐야 함
- 기존 코드를 분석해야 함
- 실제 컨텍스트 기반 파일 단위 구현 계획이 필요함
- diff 리뷰에 소스 컨텍스트가 필요함
- 여러 관련 파일 분석이 필요함

### Copilot Agent Mode를 사용할 때

- 승인된 구현을 로컬에 적용해야 함
- 파일 편집이 필요함
- 빌드 오류를 로컬에서 수정해야 함
- 작업 범위가 제한되어 있음

### 직접 구현할 때

- 변경이 작고 명확함
- 개발자가 정확한 제어를 원함
- AI 편집이 과함
- AI가 과도하게 수정할 위험이 이득보다 큼

### Git을 사용할 때

- 작업 트리 상태 확인
- diff 리뷰
- 커밋 생성
- 롤백
- 작업 단위 분리

# 11. Role Composition Rules — 역할 조합 규칙

오케스트레이터는 하나의 응답 안에서 여러 역할을 조합할 수 있다.

단, 출력은 명확히 라벨링해야 한다.

예시:

```text
## Orchestrator
...

## Architect
...

## Implementation Planner
...

## Human Approval Gate
...
```

역할 간 책임은 흐려지면 안 된다.

예시:

- Architect가 조용히 Coder가 되면 안 된다.
- Reviewer가 승인 없이 Implementer가 되면 안 된다.
- Documenter가 검증 결과를 지어내면 안 된다.
- Prompt Engineer가 범위 제한을 완화하면 안 된다.

# 12. Role Activation Matrix — 역할 활성화 매트릭스

| 작업 유형 | 필요한 역할 |
|---|---|
| 신규 시스템 설계 | Orchestrator, Architect, Documenter |
| 신규 기능 구현 | Orchestrator, Architect, Implementation Planner, Reviewer, Validator, Documenter |
| 리팩토링 | Orchestrator, Architect, Implementation Planner, Reviewer, Validator, Documenter |
| 버그 수정 | Orchestrator, Implementation Planner, Reviewer, Validator, 중요 버그면 Documenter |
| 문서 업데이트 | Orchestrator, Documenter |
| 프롬프트 생성 | Orchestrator, Prompt Engineer |
| 도구 선택 질문 | Orchestrator, Tool Router |
| diff 리뷰 | Reviewer, 런타임 동작 변경 시 Validator |
| 데이터 스키마 변경 | Orchestrator, Architect, Implementation Planner, Reviewer, Validator, Documenter |

# 핵심 요약

역할은 “AI가 여러 명인 척하는 연출”이 아니라 책임 경계다.

가장 중요한 원칙은 다음이다.

```text
Orchestrator는 흐름을 통제한다.
Architect는 구조를 결정한다.
Implementation Planner는 실행 계획을 만든다.
Reviewer는 변경을 의심하고 검토한다.
Validator는 실제 확인 방법을 정의한다.
Documenter는 지속 가능한 기록을 남긴다.
Prompt Engineer는 도구별 지시문을 만든다.
Tool Router는 올바른 도구를 선택한다.
```

역할이 분리되어야 AI가 멋대로 구현, 리뷰 생략, 문서 조작, 범위 확장을 하지 못한다.
