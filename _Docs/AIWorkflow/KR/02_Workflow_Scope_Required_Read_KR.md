# 02_Workflow_Scope 필수 확인 섹션 번역본

이 문서는 `02_Workflow_Scope.md`에서 사용자가 반드시 직접 읽어야 하는 핵심 섹션을 한국어로 번역한 보조 문서다.

원본 운영 문서는 영어로 유지한다.  
이 문서는 사용자가 판단 기준을 빠르게 확인하기 위한 읽기용 문서다.

---

# 4. 반드시 워크플로우를 사용해야 하는 작업 유형

AI 오케스트레이터 워크플로우는 아래 작업 유형에 반드시 적용한다.

## 4.1 신규 시스템 설계

새로운 게임플레이, UI, 도구, 데이터, 런타임 시스템을 도입할 때 사용한다.

예시:

- 다이얼로그 시스템
- NPC 배치 시스템
- 진행 상태 시스템
- 스킬 시스템
- 적 능력 시스템
- 파티클 Emitter 시스템
- 비디오 옵션 시스템
- 리소스 로딩 파이프라인

이유:

새 시스템은 장기적인 책임 경계를 만든다.  
따라서 임시 구조로 시작하면 안 된다.

---

## 4.2 아키텍처에 영향을 주는 리팩토링

소유권, 책임, 데이터 흐름, 생명주기, 시스템 경계에 영향을 주는 변경이면 워크플로우를 사용한다.

예시:

- `Enemy`에서 로직을 분리
- Scene 책임 분리
- 데이터 로딩과 런타임 동작 분리
- 새로운 컴포넌트 경계 도입
- Update 순서 변경
- 객체 소유권 또는 파괴 흐름 변경

이유:

아키텍처 리팩토링은 리뷰 없이 진행하면 회귀나 책임 누수를 조용히 만들 수 있다.

---

## 4.3 런타임 동작 변경

게임플레이 동작, 액터 상태, Scene 동작, 애니메이션 동작, 입력 동작, UI 동작, 시스템 생명주기에 영향을 주는 변경이면 워크플로우를 사용한다.

예시:

- 공격 동작 변경
- 이동 규칙 변경
- 상태 전이 변경
- 스폰 또는 파괴 규칙 변경
- 다이얼로그 진행 방식 변경
- Scene 초기화 또는 정리 방식 변경
- UI Update / Render 동작 변경

이유:

런타임 변경은 검증과 회귀 인식이 필요하다.

---

## 4.4 데이터 스키마 변경

구조화된 프로젝트 데이터를 추가하거나 수정할 때 사용한다.

예시:

- JSON 스키마 변경
- 적, 스킬, NPC, 스테이지, 다이얼로그, 파티클 데이터 필드 추가
- 저장 / 로드 데이터 변경
- 리소스 경로 규칙 변경
- 에셋 메타데이터 포맷 변경

이유:

데이터 스키마 변경은 콘텐츠 제작, 로더, 검증, 하위 호환성에 영향을 준다.

---

## 4.5 시스템 간 통합

여러 시스템을 연결하는 작업이면 워크플로우를 사용한다.

예시:

- 다이얼로그 이벤트가 게임 진행 상태를 변경
- NPC 배치가 데이터 로딩, Scene 스폰, 상호작용과 연결
- 스킬 데이터가 Projectile 생성과 데미지 로직에 연결
- 적 능력 데이터가 AI 상태, 이동, 공격 실행에 연결
- 비디오 옵션이 UI, 설정 저장, ScreenSystem 동작에 연결

이유:

통합 작업은 주로 책임 경계에서 문제가 발생한다.

---

## 4.6 AI가 구현에 참여하는 작업

Copilot, Codex 또는 다른 코딩 에이전트가 코드를 생성하거나 수정할 때 사용한다.

예시:

- Copilot Agent Mode 구현
- Codex 생성 패치
- AI 보조 리팩토링
- AI 생성 로더 / 매니저 코드
- AI 생성 컴포넌트 변경

이유:

AI 생성 구현에는 명확한 범위, 금지 변경, 리뷰 기준, 검증 기준이 필요하다.

---

## 4.7 Dev Log가 필요한 작업

프로젝트 기록으로 남겨야 하는 작업이면 워크플로우를 사용한다.

예시:

- 기능 완료
- 아키텍처 결정
- 중요한 리팩토링 완료
- 중요한 원인이 있는 버그 수정
- 워크플로우 규칙 변경
- 도구 동작 변경

이유:

중요한 결정은 채팅 기록 안에만 남아 있으면 안 된다.

---

# 6. 전체 워크플로우를 쓰지 않아도 되는 작업 유형

아주 단순하거나 고립된 작업에는 전체 워크플로우를 쓰지 않는다.

## 6.1 단순 상수 변경

예시:

- 빠른 테스트를 위한 숫자 튜닝
- 로컬 디버그용 값 조정
- 임시 프로토타입 상수 변경

단, 그 값이 밸런스 정책, 데이터 스키마, 여러 시스템에 영향을 준다면 워크플로우를 사용한다.

---

## 6.2 단순 에셋 교체

예시:

- PNG 파일 하나를 다른 파일로 교체
- 임시 플레이스홀더 이미지 갱신
- 로컬 테스트 에셋 이름 변경

단, 리소스 경로, 에셋 메타데이터, 로딩 규칙이 변경되면 워크플로우를 사용한다.

---

## 6.3 오타와 포맷팅

예시:

- 주석 수정
- Markdown 오타 수정
- 텍스트 포맷팅
- 로컬 노트 이름 변경

직접 처리한다.

---

## 6.4 1회성 디버그 로그

예시:

- 로컬 디버깅용 임시 로그 추가
- 임시 브레이크포인트 보조 코드 추가
- 짧게 쓰고 제거할 trace line 추가

직접 처리한다.  
단, 공식 디버그 시스템의 일부가 아니라면 커밋 전에 제거한다.

---

## 6.5 버리는 실험

예시:

- scratch 파일에서 렌더링 아이디어 테스트
- 고립된 수식 확인
- API 동작 빠른 확인

직접 실험한다.

다만 이 실험이 실제 기능 후보가 되면, 메인 프로젝트에 통합하기 전에 정식 오케스트레이터 작업으로 전환한다.

---

# 7. Escalation Conditions — 전체 워크플로우로 승격해야 하는 조건

작아 보이는 작업이라도 아래 조건 중 하나라도 해당되면 전체 워크플로우로 승격한다.

## 7.1 여러 파일이 영향을 받는 경우

서로 다른 시스템의 여러 파일에 영향을 주면 승격한다.

이유:

다중 파일 변경은 리뷰가 어렵고 책임 누수를 숨길 수 있다.

---

## 7.2 런타임 생명주기가 영향을 받는 경우

다음에 영향을 주면 승격한다.

- 초기화
- Update 순서
- Render 순서
- 파괴
- Scene 전환
- 소유권
- 등록 / 해제

이유:

생명주기 버그는 나중에 디버깅하기 어렵다.

---

## 7.3 데이터 포맷이 변경되는 경우

다음이 변경되면 승격한다.

- JSON 스키마
- Save data
- 리소스 경로 규칙
- 에셋 메타데이터
- enum 직렬화
- Loader 기대 조건

이유:

데이터 변경은 콘텐츠와 미래 호환성을 깨뜨릴 수 있다.

---

## 7.4 상태 전이가 변경되는 경우

다음에 영향을 주면 승격한다.

- Actor state
- FSM transition
- 다이얼로그 진행
- UI mode
- Skill state
- Enemy behavior state
- Player progression state

이유:

상태 버그는 간헐적인 런타임 실패를 만들기 쉽다.

---

## 7.5 AI 도구가 코드를 수정하는 경우

Copilot, Codex 또는 다른 에이전트가 코드를 쓰거나 수정하면 승격한다.

이유:

AI 실행에는 엄격한 범위, 리뷰, 검증이 필요하다.

---

## 7.6 사용자가 diff를 쉽게 리뷰하기 어려운 경우

예상 diff가 크거나 여러 영역에 걸쳐 있거나 추론하기 어렵다면 승격한다.

이유:

이 워크플로우의 목적은 AI 생성 작업을 리뷰 가능한 상태로 유지하는 것이다.

---

# 10. Human Responsibilities — 사용자 / 개발자의 책임

사용자 / 개발자는 다음을 책임진다.

- 아키텍처 승인
- 구현 범위 승인
- 워크플로우 문서 저장
- 로컬 빌드 실행
- 런타임 테스트 실행
- Git diff 확인
- 커밋 여부 결정
- 프로젝트 제약을 위반한 AI 산출물 거절
- 새 제약이 발견되었을 때 프로젝트 규칙 업데이트

AI가 확신 있게 답변했다는 이유만으로 리뷰를 생략하면 안 된다.

---

# 12. Default Scope Policy — 기본 범위 정책

범위가 불명확할 때 기본 정책은 다음이다.

```text
구현 범위는 좁힌다.
최종형 아키텍처는 유지한다.
관련 없는 작업은 뒤로 미룬다.
실행 전 승인을 요청한다.
```

이 워크플로우는 넓고 불안정한 구현보다, 작더라도 구조적으로 올바른 구현을 우선한다.

---

# 14. Scope Review Checklist — 범위 검토 체크리스트

작업에 전체 워크플로우를 실행하기 전에 아래 항목을 확인한다.

```text
[ ] 이 작업이 아키텍처 경계에 영향을 주는가?
[ ] 이 작업이 런타임 동작에 영향을 주는가?
[ ] 이 작업이 데이터 스키마에 영향을 주는가?
[ ] 이 작업이 여러 시스템을 연결하는가?
[ ] AI 코딩 도구가 파일을 수정할 예정인가?
[ ] 예상 diff가 리뷰하기 어려운가?
[ ] 이 작업에 영속적인 Dev Log가 필요한가?
```

하나라도 yes라면 전체 워크플로우 또는 최소한 축소 오케스트레이터 워크플로우를 사용한다.
