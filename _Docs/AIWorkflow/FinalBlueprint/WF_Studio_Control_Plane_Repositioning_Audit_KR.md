# Studio Control Plane 재포지셔닝 감사

## 1. 목적

이 문서는 지금까지 만든 AIWorkflow Studio를 감정 없이 다시 분류하고,
앞으로 어떤 방향으로 가져갈지 고정하기 위한 감사 문서다.

핵심 결론은 간단하다.

```text
Studio는 모든 것을 직접 하는 앱이 아니다.
Studio는 Human Director Control Plane이다.
```

즉 Studio는 코딩 에디터, 터미널, 범용 AI 채팅, RAG 플랫폼, 브라우저
자동화 엔진, 멀티 에이전트 프레임워크를 전부 직접 만들려고 하면 안 된다.

Studio는 감독자가 회사를 운영하듯이 방향, 결정, 승인, 기억, 업무 지시,
회의, 검증 자료, 완료 판단, git gate를 통제하는 운영 콘솔이어야 한다.

## 2. 최종 포지션

### Studio가 맡아야 하는 것

- 내가 지금 무엇을 판단해야 하는지 보여주기
- AI 직원들이 낸 제안, 회의 발언, 보고서를 정리하기
- 제안, 결정, 기억, 공식 설정 후보를 구분하기
- WorkOrder와 MeetingSession을 관리하기
- 승인 대상과 금지 범위를 명확히 보여주기
- Codex나 다른 도구의 실행 결과를 검증 자료로 묶기
- 완료 승인, 우려 감수, 수정 요청, 보류, 반려를 기록하기
- 커밋/푸시 전에 범위와 근거를 확인하기

### Studio가 직접 하면 비효율적인 것

- 범용 코드 에디터
- 범용 터미널
- 범용 AI 채팅
- 자체 RAG/문서 검색 플랫폼 전체
- 자체 브라우저 자동화 엔진
- 자체 멀티 에이전트 런타임 전체
- Discord 중심 UI 확장

생산성 기준은 이것이다.

```text
이미 외부 도구가 더 잘하는 일은 Studio가 다시 만들지 않는다.
Studio는 요청, 승인, 실행 결과, 검증 자료, 최종 판단만 관리한다.
```

## 3. 화면 재분류

| 화면 | 분류 | 판단 |
|---|---|---|
| 홈 | 사용자 핵심 화면 | 유지. 단, 여러 상태를 섞지 말고 "지금 내가 결정할 일" 중심으로 재설계한다. |
| 목표 기획 | 사용자 핵심 화면 | 유지. 큰 목표를 회의, 업무, 제안 후보로 쪼개는 Studio 고유 기능이다. |
| 감독자 결정함 | 사용자 핵심 화면 | 유지. 승인, 완료, 기록, 커밋 판단을 모으는 중심 화면이어야 한다. |
| 회의실 | 사용자 핵심 화면 | 유지. AI 직원 의견을 모으는 핵심 기능이다. |
| 업무 지시 | 사용자 핵심 화면 | 유지. 기획/회의 결과를 실행 가능한 WorkOrder로 넘기는 곳이다. |
| 직원 보고서 | 사용자 검토 화면 | 유지. 단, 보고서 채택/반려/기록 후보 의미를 더 명확히 해야 한다. |
| 지식/결정 | 사용자 거버넌스 화면 | 유지. 아이디어와 공식 결정을 분리하는 핵심 기능이다. |
| 검증 자료 | 사용자 검토 화면 | 유지. 완료 판단 근거를 보는 곳이다. |
| 변경 검토 | 사용자 git gate 화면 | 유지. 단, 전체 git 클라이언트가 아니라 선택 파일 commit/push 판단만 담당한다. |
| DevLog | 사용자/문서 참고 화면 | 유지. 작업 기록과 남은 위험을 확인한다. |
| 프로젝트 | 참고 화면 | 유지. 현재 프로젝트 경계와 준비 상태만 보여준다. 내부 설정을 과하게 노출하지 않는다. |
| 부서 | 참고 화면 | 유지. 매일 쓰는 작업대라기보다 조직도/책임표다. |
| AI 직원 | 참고 화면 | 유지. 직원 역할과 권한을 보는 곳이다. registry 원문은 숨긴다. |
| 실행 타임라인 | 참고/감사 화면 | 유지. 메인 작업 화면이 아니라 흐름 추적용이다. |
| 도구함 | 유지보수 화면 | 유지. 상단에는 정말 자주 쓸 3개 정도만 두고 나머지는 접거나 아래로 내린다. |
| 시스템 | 내부/관리자 화면 | 일반 사용자 흐름에서 숨긴다. |
| 정책 | 내부/관리자 화면 | 일반 사용자 흐름에서 숨긴다. 효과만 사용자 카드에 보여준다. |
| 원본 JSON / registry | 내부/디버그 | 기본 노출하지 않는다. 필요할 때만 펼쳐서 본다. |
| Discord 명령/카드 | legacy adapter | 주 UI에서 내려놓는다. 필요할 때만 보조 경로로 둔다. |

## 4. 외부 도구로 넘길 것

| 영역 | 더 적합한 외부 도구 |
|---|---|
| 코드 구현 | Codex App/CLI, Cursor, Windsurf, GitHub Copilot coding agent |
| 터미널/실행 관제 | Warp, Windows Terminal, 별도 로컬 프로세스 매니저 |
| 오래 도는 직원 런타임 | LangGraph 등 durable agent runtime |
| 문서 검색/RAG | Dify, RAGFlow, LlamaIndex |
| 브라우저 자동화 | Playwright, browser-use, Hermes |
| 게임/IP 제작 리소스 | Unity Muse, Scenario, Meshy, Leonardo, Runway, ElevenLabs 등 |

Studio는 이 도구들을 대체하지 않고, 다음만 담당한다.

- 무엇을 요청했는지
- 누가 승인했는지
- 어떤 도구가 실행했는지
- 결과가 어디에 있는지
- 검증 자료는 무엇인지
- 최종적으로 받아들였는지

- 결정으로 기록

- 기록함에 넣기

## 7. 외부 도구 도입 방향

| 도구군 | 판단 |
|---|---|
| Codex App/CLI | 계속 핵심 구현자/코드 분석자로 사용한다. |
| Warp | 사람이 쓰는 터미널/실행 관제 도구로 검토한다. Studio 대체재는 아니다. |
| LangGraph | Persistent AI Staff Agent의 장기 실행/중단/재개 런타임 후보로 실험한다. |
| Dify/RAGFlow | 문서 검색, 지식 기반, RAG 후보로 실험한다. |
| Cursor/Windsurf | 선택적 코드 편집 보조 도구다. 코어 워크플로우 필수 요소는 아니다. |
| CrewAI/AutoGen | 역할 실험에는 좋지만, 바로 Studio 코어 대체재로 삼지 않는다. |
| OpenHands/OpenClaw/Hermes/browser-use | 안전 경계가 분명해진 뒤 외부 adapter로만 검토한다. |
| 게임/IP 제작 AI 도구 | 직원들이 쓰는 전문 장비로 취급한다. governance 시스템이 아니다. |

## 8. 앞으로의 작업 묶음

### Bundle A. 제품 경계 고정

- Studio를 Human Director Control Plane으로 공식화한다.
- Discord-first 전제를 새 계획에서 제거한다.
- Discord는 optional adapter/legacy UI로 내린다.
- “직접 만들 것인가, 외부 도구에 맡길 것인가” 판단 기준을 고정한다.

### Bundle B. 화면 정리

- 시스템/정책 화면을 일반 흐름에서 숨긴다.
- 홈에서 내부 점검 버튼을 제거한다.
- 원본 JSON/registry 링크는 접힌 내부 정보로만 둔다.
- 도구함은 실제로 자주 누를 도구만 상단에 둔다.

### Bundle C. 홈과 결정함 재설계

홈은 다음 네 가지만 답해야 한다.

- 지금 내가 결정해야 할 일은 무엇인가?
- 현재 작업은 무엇인가?
- 검토해야 할 직원 보고서가 있는가?
- 완료/커밋 gate에서 막힌 것이 있는가?

나머지는 세부 화면으로 보낸다.

### Bundle D. 외부 도구 전략

- Tool Integration Policy를 만든다.
- 어떤 도구는 Studio가 직접 호출할지, 어떤 도구는 기록만 남길지 구분한다.
- 비용, 파일 수정, 외부 호출, 권한 gate를 분리한다.
- Warp, LangGraph, Dify/RAGFlow는 작은 spike로 먼저 검증한다.

### Bundle E. Studio Runtime Bridge 정리

- WorkOrder -> StaffContext -> Codex 직원 실행 -> 보고서 -> 기록 후보 흐름은 유지한다.
- 부족한 연결만 보강한다.
- LangGraph 같은 durable runtime을 검토하기 전까지 자체 멀티 에이전트 런타임을 과하게 확장하지 않는다.

### Bundle F. 실제 게임 작업 검증

- 작은 실제 게임 작업 하나를 새 구조로 태운다.
- 성공 기준은 “기능이 많다”가 아니라 “내가 덜 헷갈리고 더 빨리 판단한다”이다.

## 9. 앞으로 기능 추가 전 체크할 질문

새 기능을 만들기 전 반드시 확인한다.

1. 이 기능이 감독자의 판단, 승인, 반려, 완료에 직접 도움을 주는가?
2. 이 기능은 Studio가 반드시 가져야 하는 governance/memory/evidence 기능인가?
3. 이미 외부 도구가 더 잘하는 일인가?
4. Studio가 직접 만들지 않고 요청/결과/링크만 기록해도 되는가?
5. 사용자의 인지 부담을 줄이는가?

3번이 yes이고 2번이 no라면 Studio에 만들지 않는다.

## 10. 사용자 가이드 갱신 판단

이 문서는 현재 런타임 동작을 직접 바꾸지 않는다.

따라서 이 감사 문서 자체만으로는
`_Docs/AIWorkflow/Guide/AIWorkflow_User_Guide_KR.html`을 즉시 고칠 필요는 없다.

하지만 이후 화면 정리, 내비게이션 변경, 버튼 숨김, 외부 도구 연결 정책을
실제로 적용하면 사용자 가이드는 같은 변경 묶음에서 반드시 최신화해야 한다.

## 11. 바로 다음 권장 작업

다음 작업은 이것이다.

```text
Studio Control Plane 기준으로 화면/버튼 정리 적용
```

범위:

- 게임 파일은 건드리지 않는다.
- Studio 내비게이션과 홈/도구함 노출만 정리한다.
- 내부/관리자용 기능은 숨기거나 접는다.
- 기존 schema/API는 유지한다.
- UI가 바뀌면 한국어 사용자 가이드를 갱신한다.
- `node --check`, Studio smoke, 브라우저 확인으로 검증한다.
