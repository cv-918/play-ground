# Handoff 내부 Work Packet 정리

## 1. 목적

Handoff는 Studio 옆에 따로 존재하는 또 하나의 사용자용 시스템으로 두면 안 된다.

앞으로 Handoff는 **내부 Work Packet / 업무 전달 레이어**로 정리한다.

즉, 사용자는 “Handoff 파일”을 직접 관리하는 것이 아니라 Studio에서:

- 어떤 일을 시킬지
- 어떤 범위까지 허용할지
- 어떤 맥락을 줄지
- 어떤 결과와 검증 자료를 받아야 할지

를 확인하고 승인하면 된다.

## 2. 사용자 화면에서 쓸 말

사용자 화면에서는 가능하면 다음 용어를 쓴다.

```text
업무 봉투
실행 브리프
직원 인수인계
작업 전달
```

`Handoff`라는 말은 내부 구조나 디버그를 볼 때만 노출하는 것이 좋다.

## 3. Handoff가 유지해야 하는 가치

Handoff에서 중요한 것은 파일이나 큐 이름이 아니다.

중요한 것은 이것이다.

- 작업 범위
- 하지 말아야 할 것
- 담당 직원 또는 실행기
- 필요한 맥락
- 근거가 되는 기록
- 검증 요구사항
- 반환해야 할 검증 자료
- 결과물 형식
- 누가 누구에게 넘겼는지
- 승인/권한 경계

## 4. Studio에서 숨겨야 하는 것

일반적인 Director 화면에서는 아래를 숨긴다.

- raw queue 파일명
- 내부 worker 폴더
- 샘플 handoff 기록
- 조치가 필요 없는 violation 로그
- 의미 없는 packet ID
- 감독자 결정에 도움이 안 되는 내부 전달 방식

필요하면 내부/관리자 화면에서만 볼 수 있게 둔다.

## 5. Work Packet이 답해야 하는 질문

좋은 Work Packet은 아래 질문에 답해야 한다.

1. 직원에게 정확히 무엇을 시키는가?
2. 무엇은 하지 말아야 하는가?
3. 어떤 맥락이 공식 근거인가?
4. 무엇이 제안이고, 무엇이 결정이고, 무엇이 공식 설정인가?
5. 어떤 파일, 시스템, 도구가 범위에 들어가는가?
6. 무엇을 검증해야 하는가?
7. 어떤 검증 자료를 돌려줘야 하는가?
8. 직원이 직접 승인하거나 확정하면 안 되는 것은 무엇인가?
9. 결과는 Studio의 어디로 돌아오는가?

## 6. Context Pack과의 차이

쉽게 말하면:

```text
Context Pack = 직원이 알아야 할 것
Work Packet = 직원이 해도 되는 일
```

둘은 함께 가야 한다.

## 7. 폐기 기준

지금 Handoff를 바로 없애면 안 된다.

Studio가 아래 기능을 완전히 대체할 수 있을 때만 폐기할 수 있다.

- 작업 범위와 금지 범위 유지
- Context Pack 참조
- 역할 라우팅
- 검증/자료 요구사항
- 결과 반환 경로
- 감사 기록

그 전까지 Handoff는 내부 안전장치다.

## 8. Studio에서 보이면 좋은 것

Studio는 사용자가 이해할 수 있는 수준으로만 보여주면 된다.

- 직원이 받을 내용 미리보기
- 업무 봉투 생성 승인/반려
- 범위 축소 요청
- 돌아온 검증 자료 확인
- 결과를 제안/결정/기억/업무 지시/결과 검토로 분류

사용자가 raw Handoff 큐를 직접 관리하게 만들면 안 된다.
