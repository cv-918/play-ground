한눈에 보기

이 프로젝트의 워크플로우는 Discord를 사용자 인터페이스로 쓰고, PC Runner가 로컬 실행, 감시, 증거 수집, 검증 보고, 완료 카드를 담당하는 개발 작업 하네스입니다.

사용자가 목표로 하는 최종 사용감: 작업 지시, 위험 작업 승인, 완료 결과 리뷰, 커밋/푸시 결정만 사람이 맡고 나머지는 하네스가 처리합니다. 
1. /ai intake text:<작업 요청>
2. 승인 필요 시에만 승인
3. PC Runner가 실행, 감시, 증거 수집, 검증 보고
4. Completion Card 리뷰
5. accept / accept-concerns / request-changes / reject / defer 결정
6. task done 및 commit/push 결정

수동 Codex App/CLI 붙여넣기는 정규 경로가 아니라 수동 승격 경로입니다. PC Runner가 막혔거나 인증/어댑터 문제가 있을 때만 사용합니다.

워크플로우 시각화

정규 목표는 사용자가 Discord에서 작업을 넣고, 하네스가 실행과 증거 수집을 맡으며, 사람은 승인과 완료 판단만 하는 흐름입니다.

전체 흐름 지도

1. 작업 지시 /ai intake로 자연어 요청을 넣습니다.
사용자 명시 명령 /ai intake text:<작업 요청>
2. 접수/분류 TaskDraft, Backlog, 위험도, 실행 후보를 만듭니다.
확인 명령 /ai task review-intake id:<task_id>
3. 승인 판단 저위험은 자동 착수, 위험 작업은 승인 요청 카드에서 이유와 범위를 확인한 뒤 사람 승인에서 멈춥니다.
승인 필요 시 /ai task set-active id:<task_id> /ai task approve id:<task_id>
4. Runner 실행 workspace, session, evidence, verification을 생성합니다.
자동 착수가 안 됐을 때 /ai runner start id:<task_id> /ai runner read id:<task_id> runner-run-id:<runner_run_id>
5. 완료 리뷰 Completion Card를 보고 accept/request changes 등을 결정합니다.
완료 판단 명령 /ai completion card id:<task_id> completion-report-id:<completion_report_id> /ai runner accept-completion id:<task_id> completion-report-id:<completion_report_id> runner-run-id:<runner_run_id>
6. 완료/커밋 task done, git commit/push를 명시적으로 결정합니다.
마무리 명령 /ai task done id:<task_id> evidence:<완료 근거> /ai git commit-push message:<commit message>
하네스 자동 처리 사람 판단 지점 사용자 명시 명령

정규 경로와 수동 승격 경로

정규 경로
/ai intake
auto-handoff 또는 승인
PC Runner 실행/검증
Completion Card 리뷰
수동 승격
runner/adapter/auth 문제
/ai prepare goal
Codex App/CLI 수동 실행
/ai result audit
수동 승격은 예외 경로입니다. 정상 목표는 PC Runner가 실행, 감시, 증거 수집, 검증 보고를 맡는 것입니다.

Runner가 멈췄을 때 보는 지도

approval_required 범위와 위험도를 확인한 뒤 /ai task approve, /ai runner start를 사용합니다.
completion_review_required /ai completion card를 확인하고 /ai runner accept-completion으로 판단을 기록합니다.
done_or_commit_decision /ai task done으로 완료 처리하거나 /ai git commit-push를 명시적으로 실행합니다.

사용자와 하네스 역할

주체맡는 일하지 않는 일
Human Director 작업 지시, 위험 작업 승인, 완료 판단, 커밋/푸시 결정 반복 명령 수동 실행, 증거 파일 직접 조립
Discord Orchestrator 명령 UI, task 상태 관리, 승인 기록, 다음 명령 카드 제공 LLM 출력 최종 승인, 위험 작업 무단 실행
PC Runner workspace, session, evidence, verification, completion report/card 사람 승인 우회, 자동 commit/push
LLM/Codex TaskDraft 생성, 승인된 범위의 분석/구현 보조 최종 승인권 행사, 정책 결정 단독 수행

정규 흐름

가장 짧은 흐름

/ai intake text:"VAL task: source/data 변경 없이 PlayGround Debug x64 Visual Studio build를 검증해줘."
/ai intake text:"VAL task: source/data/schema/runtime/document 변경 없이 GameDataLoader expected files, JSON shape, ID/reference, readability를 검증해줘."

자동 착수 조건에 맞으면 하네스가 Backlog 생성, ActiveTask 선택, 승인, PC Runner 시작까지 진행합니다. 이후 Completion Card를 보고 완료를 판단합니다.

승인이 필요한 흐름

/ai intake text:<작업 요청>
/ai task set-active id:<task_id>
/ai task approve id:<task_id>
/ai runner start id:<task_id>

/ai task review-intake와 intake 응답 카드의 승인 요청 섹션에서 왜 승인이 필요한지, 무엇을 승인하는지, 무엇은 승인하지 않는지 확인합니다. note를 비워두면 하네스가 task 제목, 범위, 필수 검증, 금지 범위를 바탕으로 승인 메모를 자동 작성합니다.

완료 리뷰 흐름

/ai runner read id:<task_id> runner-run-id:<runner_run_id>
/ai completion card id:<task_id> completion-report-id:<completion_report_id>
/ai runner accept-completion id:<task_id> completion-report-id:<completion_report_id> runner-run-id:<runner_run_id>

완료 카드가 괜찮고 바로 done까지 처리해도 되는 경우에는 아래 단축 명령을 씁니다.

/ai runner accept-completion id:<task_id> completion-report-id:<completion_report_id> runner-run-id:<runner_run_id> mark-done:true

자동 착수 기준

자동 착수는 LLM이 마음대로 승인하는 기능이 아닙니다. deterministic policy가 허용하는 저위험 작업만 자동으로 ActiveTask 선택, approve, runner start까지 이어집니다.

자동 가능조건
DOC/VALP2/P3, low risk, clarification 없음, cross-check 문제 없음
WF 문서/유지보수workflow command behavior 변경이 없는 저위험 문서/metadata 정리
GAME validation/build validationsource/data/schema/runtime/document 변경이 없다고 명시된 Visual Studio Debug x64 build 검증 작업
GAME data readability validationsource/data/schema/runtime/document 변경이 없다고 명시된 GameDataLoader expected-file, JSON shape, ID/reference, readability 검증 작업

안전한 GAME build validation은 deterministic route를 사용합니다: profile=build, executor=local_cli, command_id=debug_visual_studio_build.

안전한 GAME data readability validation은 deterministic route를 사용합니다: profile=validation, executor=local_cli, command_id=game_data_loader_readability.

그 밖의 알 수 없는 validation evidence 요청은 자동 착수하지 않고 확인 질문에서 멈춥니다.

GAME source/data/schema/runtime/gameplay 변경, P0/P1, medium/high risk, UNITY 작업, 명령 동작 변경은 사람 승인에서 멈춥니다.

승인해야 하는 경우

항상 승인 필요

  • P0/P1 또는 high-risk 작업
  • 게임 소스 구현
  • 게임 데이터/schema 변경
  • save/load, lifecycle, runtime behavior 변경
  • workflow rule, approval policy, command behavior 변경
  • commit/push/release/deploy

자동화해도 되는 방향

  • TaskDraft 생성
  • workspace 준비
  • session/progress/heartbeat 기록
  • file watcher, diff snapshot, evidence 수집
  • VerificationReport, CompletionReport/Card 생성
  • Follow-up 후보 생성

완료 리뷰

Completion Card에서 아래를 확인합니다.

  1. 결과가 작업 요청과 일치하는가?
  2. VerificationReport가 PASS 또는 PASS_WITH_NOTES인가?
  3. CONCERNS가 있다면 사람이 받아들일 수 있는 우려인가?
  4. 변경 파일이 승인 범위 안인가?
  5. 검증 증거가 실제로 존재하는가?
결정의미
accept완료 인정
accept-concerns우려를 확인했고 받아들임
request-changes수정 필요
reject결과 반려
defer판단 보류

커밋/푸시

커밋/푸시는 자동화의 마지막 gate입니다. 하네스가 도와줄 수는 있지만, 명시적 명령 없이 자동으로 진행하면 안 됩니다.

/ai git commit message:<message>
/ai git push
/ai git commit-push message:<message>

메시지를 비워두면 현재 diff를 기반으로 하네스가 간단한 commit message를 만들 수 있습니다. 그래도 commit/push 실행 자체는 사용자의 명시적 명령입니다.

실제 게임 작업 투입 기준

하네스 안정화 단계에서는 실제 게임 작업을 작게 넣습니다.

좋은 작업 단위

  • source/data 변경 없는 검증 작업
  • Visual Studio Debug x64 build 검증
  • 파일 1~3개 안의 작은 data 수정
  • 하나의 loader, scene, component만 보는 작업
  • 검증 명령과 완료 기준이 명확한 작업

피해야 하는 작업 단위

  • 전투, 데이터, UI, 저장을 한 번에 바꾸는 작업
  • schema 변경과 runtime 구현을 한 task에 묶는 작업
  • 넓은 리팩터링 또는 전반 개선

막혔을 때

상태해야 할 일
approval_required작업 범위를 확인하고 /ai task approve 후 /ai runner start
completion_review_requiredCompletion Card 확인 후 /ai runner accept-completion
done_or_commit_decision/ai task done 또는 git 명령 결정
명령이 안 보임/ai bot status, 필요 시 /ai bot restart
build tool 인식 문제하네스가 MSBuild/devenv를 자동 탐지해야 하며, 사용자가 PATH를 직접 외울 필요는 없음

가이드 최신화 정책

워크플로우 명령, 승인 정책, runner profile, auto-handoff 기준, completion/git gate, 사용자 개입 단계가 바뀌는 작업은 반드시 이 HTML 가이드를 함께 갱신해야 합니다.

가이드 갱신이 필요한 변경 예시는 다음입니다.

  • 새 Discord 명령 추가, 삭제, 이름 변경, 옵션 변경
  • 정규 경로와 수동 승격 경로의 변경
  • 자동 handoff 허용/차단 기준 변경
  • approval/done/commit/push 정책 변경
  • runner profile 또는 executor routing 변경
  • Completion Card, VerificationReport, FinalizationLog 사용 방식 변경

관련 작업의 완료 조건에는 _Docs/AIWorkflow/Guide/AIWorkflow_User_Guide_KR.html 검토와 갱신 여부 판단이 포함되어야 합니다.
