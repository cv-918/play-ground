한눈에 보기

이 프로젝트의 워크플로우는 Studio Console을 기본 작업대처럼 쓰고, PC Runner가 로컬 실행, 감시, 검증 자료 수집, 검증 보고, 완료 카드를 담당하는 개발 작업 하네스입니다. Discord는 필요할 때만 쓰는 보조 UI입니다.

사용자가 목표로 하는 최종 사용감: 작업 지시, 위험 작업 승인, 완료 결과 리뷰, 커밋/푸시 결정만 사람이 맡고 나머지는 하네스가 처리합니다.
장기 제품 목표: AIWorkflow는 최종적으로 Discord bot이 아니라 Personal AI Development Studio / AI Studio Company Runtime으로 확장됩니다. 기존 하네스는 그 Studio의 운영, 승인, 실행, 검증 자료, 검증, 완료, 최종화, git gate를 맡는 core가 됩니다. 공식 설계 문서는 _Docs/AIWorkflow/FinalBlueprint/WF_Personal_AI_Development_Studio_Architecture_KR.md입니다. 첫 구현 조각은 _Docs/AIWorkflow/Studio/README.md에 있는 StaffAgent, Department, WorkOrder, MeetingSession, MemoryRecord, Proposal, Decision, Handoff, RoleRun, ToolRun 모델입니다.
Studio Console 사용: 로컬 Studio Director Console은 왼쪽 사이드바로 홈, 목표 기획, 프로젝트, 감독자 결정함, 부서, AI 직원, 회의실, 직원 보고서, 업무 지시, 지식/결정, 실행 타임라인, 변경 검토, 검증 자료, DevLog 페이지를 전환합니다. 홈은 최근 작업과 다음 행동을 보여주는 상황판이고, 감독자 결정함은 사람이 승인/반려/완료/커밋 여부를 결정해야 하는 항목만 모아둔 작업함입니다. 프로젝트는 현재 대상 프로젝트, Project Profile, 실행 도구 경계를 보여주고, 실행 타임라인은 회의, 업무 지시, 직원 보고서, Runner 실행, DevLog를 시간순으로 보여줍니다. 변경 검토는 현재 Git 작업대의 변경 파일을 사람 말로 설명하고, 선택 파일만 commit 또는 commit+push할 수 있게 합니다. 각 페이지의 카드에는 이 화면에서 할 수 있는 일이 표시됩니다. 이 항목은 버튼을 누르면 무엇이 바뀌는지 빠르게 판단하기 위한 안내입니다. AI 직원 페이지는 각 직원의 한국어 직책, 역할, 할 수 있는 일, 담당 산출물, 승인이 필요한 일을 보여줍니다. 운영 점검은 해당 직원의 권한, 금지 행위, 기억/canon 경계, 도구 경계, 산출물 상태, 회의/인수인계 기준을 읽기 전용으로 보여줍니다. 시스템과 정책은 내부 도구 아래에 접혀 있는 관리자/디버그용 화면입니다. 평소 작업에서는 신경 쓰지 않아도 됩니다. 내부 원본 보기, registry 원본, 실행 기록, 원본 JSON은 일반 진행 버튼이 아니라 registry와 검증 자료 원본을 확인하는 관리자/디버그용 링크입니다. 일반 화면에서는 접힌 영역 안에 들어가며, 평소에는 열지 않아도 됩니다.
Studio에서 직접 할 수 있는 일: 홈에서 새 작업 접수와 현재 다음 행동 확인을 할 수 있습니다. Studio 점검은 새 기능 추가 후 주요 페이지, schema, 핵심 카운트, 수동 smoke 순서를 읽기 전용으로 확인합니다. 목표 기획에서는 큰 목표를 입력해 추천 부서, 추천 AI 직원, 회의 후보, 업무 지시 후보, 제안 후보, 승인 항목으로 먼저 쪼갤 수 있습니다. 이 단계는 기획 기록만 만들며 공식 설정 확정, 소스 수정, task 실행, commit/push를 하지 않습니다. 감독자 결정함에서 작업 착수 승인, 완료 승인/우려 감수/수정 요청/판단 보류, 직원 보고서 후보 결정, 제안 판단, 커밋/푸시 판단을 진행합니다. 프로젝트에서 현재 프로젝트 프로필, 검증/빌드 경계, 도구 사용 경계를 확인합니다. 실행 준비 점검은 어떤 빌드/검증 프로필과 도구가 준비되어 있는지, 어떤 도구가 파일 수정/외부 호출/비용/승인 영향을 갖는지 읽기 전용으로 보여줍니다. 부서에서는 부서 책임, 검토 기준, 담당 결과물을 확인하고 해당 부서의 직원/업무로 이동할 수 있습니다. 회의실에서는 회의를 만들고 발언을 추가하며, 회의 진행안으로 다음 발언자와 다음 행동을 확인하고, 회의 운영판으로 누가 아직 말하지 않았는지, 어떤 제안/우려/질문이 남았는지, 무엇을 결정해야 회의를 닫을 수 있는지 확인합니다. AI 직원 발언 계획/실행을 요청하고, 회의 결과를 후속 업무 지시나 감독자 결정으로 넘길 수 있습니다. 업무 지시에서는 업무 지시서를 만들 수 있고, 직원 자료 미리보기/저장, 직원 실행 계획, 명시적 직원 실행, 작업 목록 생성을 할 수 있습니다. 직원 보고서에서는 AI 직원이 만든 결과를 보고서 만들기로 읽기 좋게 내보내고, 필요한 내용만 기록 후보 보기 또는 기록함에 넣기로 넘길 수 있습니다. 지식/결정에서는 제안, 결정, 기억을 기록해 아이디어, 감독자 결정, 프로젝트 기억을 분리해서 관리합니다. 전환 계획으로 “이 항목이 아직 아이디어인지, 결정인지, 기억인지, 공식 설정인지”와 “받아들이면 실제로 무엇이 바뀌는지”를 먼저 확인한 뒤 제안은 결정으로, 결정은 기억 또는 공식 설정 기억으로 넘길 수 있습니다. 실행 타임라인에서는 최근 활동의 순서를 확인하고 관련 화면으로 이동합니다. 변경 검토에서는 변경 파일의 의미를 확인하고 선택 파일만 commit 또는 commit+push합니다. 검증 자료에서는 결과 보기, 검증 보고서, 완료 보고서, 완료 카드의 차이를 보고 완료 판단 근거를 확인합니다. 완료 판단안은 완료 승인, 우려 감수 후 완료, 수정 요청, 판단 보류가 각각 언제 쓰이고 무엇을 바꾸는지 읽기 전용으로 설명합니다. 우려 사항은 “무엇을 하다 멈췄는지”, “어떤 파일 신호가 범위를 벗어났는지”처럼 사람이 판단할 수 있는 문장으로 표시됩니다. DevLog에서는 작업 배경, 범위, 검증, 남은 위험 기록을 확인합니다. 시스템에서는 프로젝트 프로필, 도구 어댑터, 도구 요청서를 확인하고, 도구 실행 전에 어떤 도구를 왜 쓰려는지와 어떤 검증 자료가 필요한지 요청서로 남길 수 있습니다. 이 화면은 내부/관리자용입니다. 정책의 자동 진행 준비도는 현재 작업이 왜 자동 진행될 수 있거나 없는지, 어떤 단계는 자동 가능하고 어떤 단계는 항상 사람이 판단해야 하는지 읽기 전용으로 보여줍니다. 이 화면은 내부/관리자용입니다. 이 버튼들은 기존 AIWorkflow gate를 우회하지 않고, 선택한 task와 선택한 파일에 대해서만 동작합니다.
Studio 버튼의 의미: 직원 자료 미리보기는 업무 지시를 특정 AI 직원이 읽을 실행 문맥으로 어떻게 묶을지 보여줍니다. 직원 자료 저장은 그 문맥을 내부 문맥 기록에 남깁니다. 직원 실행 계획은 Codex 직원 실행 전에 어떤 모델/명령/입력이 쓰일지 점검합니다. 직원 실행은 signed-in Codex CLI를 read-only 직원 실행으로 호출하고 결과를 _Temp 검증 자료로 남깁니다. 보고서 만들기는 직원 실행 결과를 사람이 읽기 좋은 HTML 검토 자료로 내보냅니다. 기록 후보 보기는 직원 보고서에서 제안, 기억, 업무 지시, 인수인계 후보가 무엇인지 미리 보여줍니다. 기록함에 넣기는 필요한 후보를 Studio 기록 후보로 남깁니다. 이것은 실행 승인, 공식 설정 확정, task 생성이 아닙니다. AI 발언 계획은 회의 주제와 참가자 기준으로 직원 발언 실행 전에 어떤 문맥과 명령이 쓰일지 보여줍니다. AI 발언 실행은 저장된 회의에 한해 AI 직원 발언을 생성하고 회의 발언으로 추가합니다. 결과 보기는 Runner 실행 기록과 생성된 원본 보고서로 들어가는 입구입니다. 검증 보고서는 무엇을 검사했고 어떤 경고가 있었는지 보는 자료입니다. 완료 카드는 사람이 완료 승인, 수정 요청, 우려 감수 여부를 판단하기 위한 짧은 요약입니다. ToolRun Request 만들기는 도구를 실행하기 전에 adapter, 권한 등급, 목적, 입력, 기대 산출물, 필수 검증 자료를 검토 가능한 요청서로 남깁니다. 이 요청서는 실행 허가가 아니며, 비용/외부 호출/파일 변경 가능성이 있는 도구는 별도 승인 gate를 거칩니다. 이 실행은 소스 수정, 공식 설정 기록, task 승인, task done, commit, push를 직접 하지 않습니다.
Studio 홈의 AIWorkflow Core: Discord를 쓰지 않는 흐름에서는 Studio Console의 홈이 기본 상황판입니다. AIWorkflow Core는 현재 ActiveTask, 최근 Runner 중단 이유, 완료 검토 상태, Backlog 요약을 보여줍니다. Git / 검증 자료는 현재 branch, 변경 파일 수, 검증 판정, 완료 보고서/완료 카드 링크를 보여줍니다. 즉, “지금 뭘 판단해야 하는지”는 먼저 홈의 AIWorkflow Core에서 확인하고, 실제 결정은 감독자 결정함 또는 해당 세부 화면에서 진행합니다. 
1. Studio 홈의 새 작업 접수에 작업 요청 입력
2. 승인 필요 시에만 승인+실행
3. PC Runner가 실행, 감시, 검증 자료 수집, 검증 보고
4. 감독자 결정함 또는 검증 자료에서 완료 카드와 결과 확인
5. 완료 승인 / 우려 감수 후 완료 / 수정 요청 / 반려 / 판단 보류 결정
6. 변경 검토에서 선택 파일만 commit/push 결정
7. DevLog에서 기록과 남은 위험 확인

수동 Codex App/CLI 붙여넣기는 정규 경로가 아니라 수동 승격 경로입니다. PC Runner가 막혔거나 인증/어댑터 문제가 있을 때만 사용합니다. Discord adapter를 쓰는 경우 상태 의미나 다음 행동이 헷갈리면 /ai ask로 물어볼 수 있습니다.

워크플로우 본체

이 항목은 Discord 명령, 버튼, 카드 같은 디스패치 UI를 제외하고도 반드시 유지되어야 하는 AIWorkflow의 전체 구조를 설명합니다.

핵심 원칙: 사람은 목표, 승인, 완료 판단, 커밋 결정을 맡고, 하네스는 작업 상태, 실행 상태, 검증 자료, 검증, 최종화 기록을 분리해서 남깁니다.

코어 워크플로우 전체 지도: 총 12단계

1. Work Request Intake / 작업 요청 접수 사람이 목표, 기대 결과, 금지 범위, 검증 기대치를 제시합니다.
2. Intent Structuring / 의도 구조화 자연어 요청을 TaskDraft 또는 GoalIntent 형태로 바꾸고, 모호하면 실행하지 않습니다.
3. Task Lifecycle Registration / 작업 상태 등록 Backlog, ActiveTask 후보, category, kind, priority, risk, workflow path를 기록합니다.
4. Risk And Approval Policy Evaluation / 위험도와 승인 정책 평가 자동 진행 가능, 사람 승인 필요, 차단 또는 보강 필요 여부를 deterministic rule로 판단합니다.
5. Human Approval Gate / 사람 승인 지점 필요한 경우 실제 변경 대상, 금지 범위, 검증 조건을 보고 Human Director가 승인합니다.
6. Runtime Workspace Preparation / 실행 작업공간 준비 task_id 기준 workspace와 runner 산출물 위치를 만들고 실행 경계를 분리합니다.
7. Executor Run And Session Supervision / 실행기 구동과 세션 감시 승인된 profile과 executor만 실행하고, start/end, heartbeat, stop reason을 기록합니다.
8. Evidence Collection And Diff Snapshot / 검증 자료 수집과 diff snapshot 로그, exit code, 변경 파일, diff, build/test 결과를 모읍니다. 이 단계는 pass/fail을 판정하지 않습니다.
9. VerificationReport Generation / 검증 보고서 생성 수집된 검증 자료를 기준으로 PASS, PASS_WITH_NOTES, CONCERNS, BLOCKED, FAIL을 판정합니다.
10. CompletionReport And Completion Card / 완료 보고서와 완료 카드 사람이 완료 여부를 판단할 수 있도록 결과, 남은 우려, 검증 근거를 요약합니다.
11. Human Completion Decision And FinalizationLog / 완료 판단과 최종화 기록 완료 승인, 우려 감수, 수정 요청, 반려, 판단 보류 중 하나를 기록합니다.
12. Task Done And Git Gate / 작업 완료와 git 결정 task done 여부를 확정하고, commit/push는 마지막 사람 결정으로 별도 실행합니다.
사람 명시 결정 정책/승인 판단 지점 하네스 자동 처리
이 12단계가 워크플로우의 본체입니다. Discord는 이 단계를 조작하기 위한 UI일 뿐이며, UI가 바뀌어도 단계와 책임 경계는 유지됩니다.

1. 작업 접수와 의도 구조화

  • 자연어 요청은 바로 실행하지 않고 TaskDraft 또는 구조화된 작업 상태로 변환합니다.
  • 분류에는 category, kind, priority, risk, workflow path, non-goals, validation이 포함됩니다.
  • 모호한 요청은 실행하지 않고 사람 확인 또는 보강이 필요한 상태로 멈춥니다.
  • LLM은 의도 해석과 초안 생성을 도울 수 있지만, 최종 승인 권한은 갖지 않습니다.

2. 작업 상태와 실행 상태 분리

상태 계층담당하는 내용하면 안 되는 일
Task LifecycleBacklog, ActiveTask, approval, blocked/deferred/done 상태실행 로그나 세션 성공 여부를 직접 판정하지 않음
Runtime Workspacetask_id 기준 작업 공간과 런타임 산출물 위치승인 없이 소스나 데이터를 바꾸지 않음
Session State실행 세션, heartbeat, progress, stop reason검증 통과/실패를 최종 판정하지 않음
Evidence / 검증 자료로그, exit code, 변경 파일, diff snapshot, build/test 결과검증 자료 수집만으로 task done 처리하지 않음
Verification/Completion검증 판정, 완료 보고서, 완료 카드, 남은 우려commit/push를 자동 실행하지 않음

3. 승인 정책

  • 저위험 반복 검증은 정책 조건이 맞을 때만 자동 착수 후보가 됩니다.
  • P0/P1, high-risk, source/data/schema/runtime/save/load/lifecycle 변경은 사람 승인에서 멈춥니다.
  • 승인은 “작업 범위 안에서”라는 추상 문구가 아니라, 실제로 바뀔 파일/영역/행동과 금지 범위를 보고 결정해야 합니다.
  • 승인 이력, 반려 사유, 우려 감수, 수정 요청은 ApprovalHistory와 FinalizationLog로 추적합니다.

4. 실행과 감시

  • PC Runner는 작업별 workspace에서 승인된 executor와 profile만 실행합니다.
  • 실행기는 Codex CLI, Local CLI, 이후 추가될 도구처럼 교체 가능해야 하지만, start/end 감지, 로그 수집, 실패/timeout 처리, 변경 파일 추적이 가능해야 합니다.
  • Session Supervisor는 실행 중인지, 멈췄는지, 어떤 이유로 멈췄는지를 기록합니다.
  • Evidence Collector(검증 자료 수집기)는 실행 결과와 diff 같은 검증 자료를 모으지만, 통과 판정이나 완료 처리는 하지 않습니다.

5. 검증과 완료 판단

  • VerificationReport는 검증 자료를 읽어 PASS, PASS_WITH_NOTES, CONCERNS, BLOCKED, FAIL 같은 판정을 만듭니다.
  • CompletionReport와 Completion Card는 사람이 완료를 받아들일지 판단하기 위한 요약입니다.
  • CONCERNS는 실패가 아닐 수도 있지만, 사람이 무엇을 감수하는지 알아야 완료로 넘길 수 있습니다.
  • 수정이 필요하면 원 task를 억지로 done 처리하지 않고 focused fix task로 분리합니다.

6. 최종화와 git gate

  • 완료 승인, 우려 감수, 수정 요청, 반려, 판단 보류는 모두 FinalizationLog에 남깁니다.
  • task done은 완료 판단 이후에만 가능하며, 검증이 없거나 우려가 해결되지 않았으면 done으로 넘기지 않습니다.
  • commit/push는 마지막 사람 결정 gate입니다. 하네스가 메시지를 제안하거나 실행을 도울 수는 있지만, 명시적 결정 없이 자동 commit/push하면 안 됩니다.
  • 워크플로우 규칙, 명령, 승인 정책, 완료 gate가 바뀌면 이 사용자 가이드도 같은 변경 묶음에서 갱신해야 합니다.
이 섹션은 Discord 디스패치가 바뀌거나 사라져도 유지되어야 하는 코어입니다. UI가 Discord, Codex App, 다른 도구로 바뀌어도 작업 상태, 실행 상태, 검증 자료, 검증, 승인, 최종화, git gate의 분리는 유지해야 합니다.

워크플로우 시각화

정규 목표는 사용자가 Discord에서 작업을 넣고, 하네스가 실행과 검증 자료 수집을 맡으며, 사람은 승인과 완료 판단만 하는 흐름입니다.

전체 흐름 지도

1. 작업 지시 /ai intake로 자연어 요청을 넣습니다.

승인 필요 시 /ai task review-intake id:<task_id> /ai task approve-runner id:<task_id>

정규 흐름

가장 짧은 흐름

/ai intake text:"VAL task: source/data 변경 없이 PlayGround Debug x64 Visual Studio build를 검증해줘."
/ai intake text:"VAL task: source/data/schema/runtime/document 변경 없이 GameDataLoader expected files, JSON shape, ID/reference, readability를 검증해줘."

자동 착수 조건에 맞으면 하네스가 Backlog 생성, ActiveTask 선택, 승인, PC Runner 시작까지 진행합니다. 이후 Completion Card를 보고 완료를 판단합니다.

승인이 필요한 흐름

/ai intake text:<작업 요청>
/ai task review-intake id:<task_id>
/ai task approve-runner id:<task_id>

approve-runner는 범위를 승인한 뒤 ActiveTask 선택, 승인 기록, PC Runner 백그라운드 시작을 한 번에 처리하는 권장 명령입니다. set-active, approve, runner start 같은 세부 단계는 일반 slash 검색에 숨겨진 복구용 경로입니다.

Discord 카드에 버튼이 보이면 버튼이 우선입니다. 승인 내용 보기는 승인 대상과 제외 범위를 보여주고, 승인+실행은 승인 기록과 Runner 시작을 한 번에 처리합니다. 명령어는 버튼이 없거나 실패했을 때의 예비 경로입니다.

Runner 시작은 자동 handoff, 승인+실행 버튼, 또는 /ai task approve-runner가 처리합니다. 진행 상태는 /ai runner status와 /ai runner read로 확인합니다.

/ai task review-intake와 intake 응답 카드의 승인 요청 섹션은 짧은 bullet로 표시됩니다. 확인할 것은 세 가지입니다.

  • 왜 사람 승인이 필요한가?
  • 승인하면 어떤 파일/영역에 어떤 변경을 시도하는가?
  • 승인하지 않는 범위는 무엇인가?

승인 카드의 승인하면 하네스가 시도할 변경과 대상/근거가 비어 있거나 모호하면 승인하지 말고, 먼저 /ai ask로 물어보거나 task 내용을 보강합니다. “task 범위 안에서” 같은 표현만으로는 충분한 승인 근거가 아닙니다.

note를 비워두면 하네스가 task 제목, 범위, 필수 검증, 금지 범위를 바탕으로 승인 메모를 자동 작성합니다.

범위를 검토했고 권장안대로 착수해도 된다면 /ai task approve-runner id:<task_id> 하나로 ActiveTask 선택, 승인 기록, PC Runner 백그라운드 시작을 함께 처리할 수 있습니다.

완료 리뷰 흐름

/ai runner read id:<task_id> runner-run-id:<runner_run_id>
/ai completion card id:<task_id> completion-report-id:<completion_report_id>

완료 카드가 괜찮고 바로 done까지 처리해도 되는 경우에는 완료 카드의 완료 승인 버튼을 씁니다.

완료 승인 버튼이 성공하면 task done은 이미 처리된 것입니다. 이후 응답에 task done: yes가 보이면 완료 처리를 다시 실행하지 말고, 필요한 경우 /ai git commit-push만 결정합니다.

완료 리뷰 카드의 완료 카드, 완료 승인, 우려 감수 후 완료, 커밋+푸시 버튼은 복사할 명령 대신 쓰는 기본 UI입니다. 각 버튼은 이름 그대로 한 단계만 처리하며, commit/push는 별도 버튼을 눌러야 실행됩니다.

완료 카드가 CONCERNS이지만 blocker나 failed check가 없고, 사람이 우려를 확인한 뒤 감수하기로 결정했다면 우려 감수 후 완료 버튼을 사용합니다. 이 버튼은 작업을 폐기하거나 우려를 숨기는 기능이 아니라, 우려를 검토했다는 기록을 남기고 task done으로 진행하는 결정입니다.

자동 착수 기준

자동 착수는 LLM이 마음대로 승인하는 기능이 아닙니다. deterministic policy가 허용하는 저위험 작업만 자동으로 ActiveTask 선택, approve, runner start까지 이어집니다.

자동 가능조건
DOC/VALP2/P3, low risk, clarification 없음, cross-check 문제 없음
WF 문서/유지보수workflow command behavior 변경이 없는 저위험 문서/metadata 정리
GAME validation/build validationsource/data/schema/runtime/document 변경이 없다고 명시된 Visual Studio Debug x64 build 검증 작업
GAME data readability validationsource/data/schema/runtime/document 변경이 없다고 명시된 GameDataLoader expected-file, JSON shape, ID/reference, readability 검증 작업

안전한 GAME build validation은 deterministic route를 사용합니다: profile=build, executor=local_cli, command_id=debug_visual_studio_build.

안전한 GAME data readability validation은 deterministic route를 사용합니다: profile=validation, executor=local_cli, command_id=game_data_loader_readability.

자동 handoff가 허용된 경우 /ai intake는 Backlog 생성, ActiveTask 선택, 승인 기록, PC Runner 백그라운드 시작까지 처리합니다. 이후 진행 상황은 /ai runner status id:<task_id>와 /ai runner read id:<task_id>로 확인합니다.

schema 변경 없음만으로는 GAME 작업이 자동 착수되지 않습니다. GAME data task, data 수정, 필요한 최소 수정, json 수정처럼 실제 수정이 포함되면 작은 작업이어도 사람 승인에서 멈추는 것이 정상입니다.

백그라운드 시작 직후의 intake 응답에는 아직 completion-report-id와 runner-run-id가 없을 수 있습니다. 이때 다음 명령이 /ai runner status, /ai runner read 두 개만 나오는 것은 정상입니다. /ai runner read를 실행하면 완료 카드와 accept-completion에 필요한 실제 ID가 표시됩니다.

가이드의 <task_id>, <completion_report_id>, <runner_run_id>는 예시 자리표시자입니다. Discord에 그대로 입력하지 말고 응답 카드에 표시된 실제 값으로 바꿔서 사용합니다.

ephemeral은 Discord의 “나만 보이는 메시지”가 아니라 Codex CLI exec --ephemeral입니다. intake 해석용 임시 실행으로, Codex 세션 기록을 오래 남기지 않는 1회성 분류 실행에 사용합니다.

그 밖의 알 수 없는 validation evidence(검증 자료) 요청은 자동 착수하지 않고 확인 질문에서 멈춥니다.

GAME source/data/schema/runtime/gameplay 변경, P0/P1, medium/high risk, UNITY 작업, 명령 동작 변경은 사람 승인에서 멈춥니다.

승인해야 하는 경우

항상 승인 필요

  • P0/P1 또는 high-risk 작업
  • 게임 소스 구현
  • 게임 데이터/schema 변경
  • save/load, lifecycle, runtime behavior 변경
  • workflow rule, approval policy, command behavior 변경

  • Follow-up 후보 생성

완료 리뷰

Completion Card에서 아래를 확인합니다.

  1. 결과가 작업 요청과 일치하는가?
  2. VerificationReport가 PASS 또는 PASS_WITH_NOTES인가?
  3. CONCERNS가 있다면 사람이 받아들일 수 있는 우려인가?
  4. 변경 파일이 승인 범위 안인가?
  5. 검증 자료가 실제로 존재하는가?

PASS_WITH_NOTES는 검증 통과에 가까운 상태지만 자동 완료 신호는 아닙니다. notes를 사람이 읽고 받아들일 수 있을 때만 완료 승인 또는 우려 감수 후 완료로 진행합니다.

완료 카드 버튼은 명령어 복붙 대신 쓰는 기본 UI입니다. 완료 승인은 accept와 task done을 처리하고, 수정 요청은 request-changes를 기록하며, 판단 보류는 defer를 기록합니다. CONCERNS가 있지만 blocker나 failed check가 없고 사람이 우려를 감수하기로 결정했다면 우려 감수 후 완료를 사용합니다. 이 결정은 작업을 폐기하거나 우려를 우회하는 뜻이 아니라, 우려를 확인했다는 기록을 남기고 task done으로 넘기는 뜻입니다.

결과 보기는 Runner가 실제로 무엇을 실행했고 어떤 로그, 세션, 보고서를 만들었는지 확인하는 버튼입니다. 완료 카드는 그 결과를 사람이 완료로 받아들일 수 있는지 판단하기 위한 요약 카드입니다. 문제가 생기면 먼저 결과 보기로 원인을 보고, 완료 카드에서 완료 승인/수정 요청/우려 감수 여부를 결정합니다.

완료 카드의 남은 이슈에는 실패 또는 취소된 실행 세션이 사람 말로 표시됩니다. 예를 들어 Codex CLI가 프롬프트를 UTF-8로 읽지 못해 시작 단계에서 실패한 경우, “Codex CLI가 실제 수정 지시를 읽고 실행하던 단계가 실패했고, 작업 지시 프롬프트 인코딩 때문에 멈췄다”처럼 원인 신호를 함께 확인합니다.

수정 요청을 누른 뒤에는 task done이나 commit/push로 가지 않습니다. 최종화 카드의 수정 작업 접수 버튼을 눌러 방금 request_changes가 난 CompletionReport/FinalizationLog 기준의 focused fix task를 새로 접수합니다.

/ai auto-approval apply는 기본 설정에서 차단됩니다. 나중에 apply 설정이 켜지고 정책 평가가 자동 적용 가능 상태를 낼 때만 task done을 적용할 수 있으며, commit/push는 계속 별도 결정입니다.

결정의미
accept완료 인정
accept-concerns우려를 확인했고 감수함. task done으로 진행하지만 commit/push는 별도 결정
request-changes수정 필요
reject결과 반려
defer판단 보류

커밋/푸시

커밋/푸시는 자동화의 마지막 gate입니다. 하네스가 도와줄 수는 있지만, 명시적 명령 없이 자동으로 진행하면 안 됩니다.

/ai git commit message:<message>
/ai git push
/ai git commit-push message:<message>

메시지를 비워두면 현재 diff를 기반으로 하네스가 간단한 commit message를 만들 수 있습니다. 그래도 commit/push 실행 자체는 사용자의 명시적 명령입니다.

실제 게임 작업 투입 기준

하네스 안정화 단계에서는 실제 게임 작업을 작게 넣습니다.

좋은 작업 단위

  • source/data 변경 없는 검증 작업
  • Visual Studio Debug x64 build 검증
  • 파일 1~3개 안의 작은 data 수정. 단, 실제 수정은 자동 착수하지 않고 사람 승인 후 진행
  • 하나의 loader, scene, component만 보는 작업
  • 검증 명령과 완료 기준이 명확한 작업

피해야 하는 작업 단위

  • 전투, 데이터, UI, 저장을 한 번에 바꾸는 작업
  • schema 변경과 runtime 구현을 한 task에 묶는 작업
  • 넓은 리팩터링 또는 전반 개선

막혔을 때

상태 이름이나 다음 버튼이 헷갈리면 먼저 /ai ask text:<질문>을 사용합니다. 특정 작업을 물어볼 때는 /ai ask id:<task_id> text:<질문>처럼 작업 ID를 함께 넣습니다.

/ai ask text:GAME-001 partial_done이면 다음에 뭐해?
/ai ask text:completion_review_required면 뭐 눌러?
/ai ask text:game 20260514 172323 이 무슨 작업이야?

작업 ID는 GAME-001, GAME001, 게임001, 게임-001, game 20260514 172323처럼 입력할 수 있습니다. 한글 별칭은 게임/GAME, 문서/DOC, 검증/VAL, 워크/WF, 유니티/UNITY로 해석됩니다.

“무슨 작업이야?”라고 물으면 하네스는 단순 상태가 아니라 작업 목적, 원래 작업, 근거 FinalizationLog/CompletionReport, 금지 범위, 다음 행동을 짧게 설명해야 합니다.

가이드 최신화 정책

워크플로우 명령, 승인 정책, runner profile, auto-handoff 기준, completion/git gate, 사용자 개입 단계가 바뀌는 작업은 반드시 이 HTML 가이드를 함께 갱신해야 합니다.

가이드 갱신이 필요한 변경 예시는 다음입니다.

  • 새 Discord 명령 추가, 삭제, 이름 변경, 옵션 변경
  • 정규 경로와 수동 승격 경로의 변경
  • 자동 handoff 허용/차단 기준 변경
  • approval/done/commit/push 정책 변경
  • runner profile 또는 executor routing 변경
  • Completion Card, VerificationReport, FinalizationLog 사용 방식 변경

관련 작업의 완료 조건에는 _Docs/AIWorkflow/Guide/AIWorkflow_User_Guide_KR.html 검토와 갱신 여부 판단이 포함되어야 합니다.
