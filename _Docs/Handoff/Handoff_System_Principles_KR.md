# AI Role Handoff System 운영 원칙

## 고정 이름

앞으로 이 작업은 아래 이름으로 고정한다.

```text
전체 시스템명: AI Role Handoff System
짧은 이름: Handoff System
저장소 기능명: Handoff
통합 작업명: AIWorkflow Handoff Integration
한국어 설명명: 역할별 AI 업무 인수인계 시스템
```

## 목적

AI Role Handoff System은 역할별 AI 채팅 또는 담당자들이 작업을 주고받기 위한 공용 업무 교환 계층이다.

Planner, Developer, Artist, Reviewer, QA 같은 역할이 서로에게 넘겨야 하는 기획서, 요청서, 리소스 안내, 리뷰 요청, QA 요청, 완료 보고를 저장소 문서로 남긴다.

목표 사용감은 사용자가 주로 메인 기획자 채팅과 기획 대화를 하고, 기획이 승인되면 각 역할 채팅이 Handoff 공간에서 자기 일을 찾아 계획하고 진행하며, 필요한 경우에만 사용자에게 승인 요청을 올리는 것이다.

## AIWorkflow와의 관계

Handoff는 AIWorkflow를 대체하지 않는다.

각 시스템의 역할은 다음과 같다.

```text
Handoff = 역할 간 업무 큐, 전달 인터페이스, 가시화 계층
AIWorkflow = 승인, 위험도, 검증, 완료 판정의 안전 엔진
DevLog = 완료된 작업과 조사/수정 이력
Git = 실제 저장소 변경 이력
```

필수 관계는 다음과 같다.

```text
Handoff는 AIWorkflow 규칙을 호출한다.
Handoff는 AIWorkflow 규칙을 복제하거나 덮어쓰지 않는다.
```

Handoff 문서가 `_Docs/AIWorkflow/` 또는 `AGENTS.md`와 충돌하면, AIWorkflow와 `AGENTS.md`가 우선한다. 이 경우 역할 채팅은 작업을 멈추고 충돌을 보고해야 한다.

## 기본 운영 흐름

1. 사용자와 Planner가 기획 또는 방향을 논의한다.
2. 사용자가 기획 방향을 승인한다.
3. Planner는 필요한 기획 브리프, 요청서, 참고 자료, 완료 기준을 Handoff에 작성한다.
4. 받는 역할은 `_Docs/Handoff/`에서 자기 역할을 향한 작업을 확인한다.
5. 받는 역할은 실행 전에 먼저 계획을 작성하거나 갱신한다.
6. 승인된 범위 안의 낮은 위험 문서 작업은 진행할 수 있다.
7. 높은 위험 작업은 반드시 명시적 사용자 승인을 기다린다.
8. 결과, 리뷰 요청, QA 요청, 완료 노티, 남은 위험은 Handoff와 필요한 DevLog에 다시 기록한다.

## 승인 모델

기획 승인과 실행 승인은 다르다.

```text
기획 승인
= 이 기능, 콘텐츠, 디자인, 방향으로 간다는 것을 사용자가 받아들임

실행 승인
= 특정 역할이 특정 파일, 데이터, 런타임 동작, 도구, Git 상태를 바꿔도 된다고 사용자가 허용함
```

Handoff 항목이 `Ready`라는 뜻은 받는 역할이 확인할 준비가 되었다는 뜻이다.

`Ready`는 소스 코드, 데이터, 런타임 동작, 도구 실행, 커밋, 푸시가 승인되었다는 뜻이 아니다.

다음 작업은 여전히 AIWorkflow 승인 게이트를 따른다.

- 소스 코드 구현
- 구조적 리팩터링
- 프로젝트 소스 디렉터리 파일 생성
- JSON 스키마 변경
- 저장/로드 동작 변경
- Actor 또는 Scene 생명주기 변경
- 런타임 동작 변경
- 빌드 설정 변경
- 파일을 수정할 수 있는 도구 실행
- 커밋과 푸시
- 워크플로우 규칙 변경

승인은 명시된 범위에만 적용된다. 범위가 바뀌면 역할 채팅은 다시 멈추고 승인을 받아야 한다.

## 실질 변경 내용 기반 승인 요청 규칙

승인 요청은 실제로 무엇을 바꾸려는지 설명해야 한다.

사용자 관점의 승인 대기 확인과 결정 흐름은 `Approval_Waiting_Flow_KR.md`에 정의한다.

다음처럼 게이트 이름만 말하는 승인 요청은 충분하지 않다.

```text
런타임 동작 변경이라 승인 필요합니다.
```

승인 요청은 게임, 워크플로우, 데이터, 저장소에 어떤 변화가 생기는지를 설명해야 한다.

높은 위험 승인 요청에는 다음 항목이 들어가야 한다.

- 무엇을 바꾸려는가
- 플레이어, 사용자, 게임, 워크플로우, 저장소 관점에서 어떤 동작이 생기는가
- 왜 필요한가
- 어떤 데이터 또는 코드 개념이 영향을 받는가
- 어떤 파일을 바꿀 예정인가
- 무엇은 하지 않을 것인가
- 알려진 위험은 무엇인가
- 어떻게 검증할 것인가
- 사용자에게 어떤 결정을 원하는가

승인 요청이 실질 변경 내용을 설명하지 못하면, 그 역할은 아직 승인을 요청할 자격이 없다. 먼저 승인 요청서를 다시 작성해야 한다.

## 사용자 승인 대기 방식

높은 위험 작업은 눈에 보이게 기다려야 한다.

기다린다는 뜻은 다음과 같다.

- 소스 코드, JSON 스키마, 런타임 데이터, 프로젝트 파일, 빌드 설정, Git 상태를 변경하지 않는다.
- Handoff 항목을 완료로 표시하지 않는다.
- 완료된 작업처럼 다음 역할에게 넘기지 않는다.
- 승인 요청 문서 경로를 Handoff 색인 또는 항목 내부에 기록한다.
- 사용자가 승인, 거절, 범위 수정을 판단할 수 있게 요청 결정을 명확히 적는다.

사용자는 `_Docs/Handoff/00_Index.md`를 보면 승인 대기 작업을 찾을 수 있어야 한다.

## 낮은 위험 자동 작업의 경계

이후 Phase에서 명시적으로 확장하기 전까지, 낮은 위험 자동 작업은 문서-only Handoff 유지 관리에 한정한다.

예:

- Handoff 문서 읽기
- 내 역할에 해당하는 작업 요약
- Handoff 문서의 상태 문구 갱신
- 계획서 작성
- 승인 요청서 작성
- 결과 문서 또는 리뷰 요청서 작성

낮은 위험 작업에는 소스 코드 변경, 데이터 스키마 변경, 런타임 동작 변경, 빌드/테스트 실행, 커밋, 푸시, 릴리스, 배포가 포함되지 않는다.

## Phase 1 범위

이 문서는 AIWorkflow Handoff Integration의 Phase 1이다.

Phase 1은 운영 원칙만 확정한다.

Phase 1에서는 다음을 구현하지 않는다.

- Packet 디렉터리 구조
- manifest 스키마
- 역할별 루틴 문서
- 읽기 전용 스캐너 자동화
- claim/status 자동화
- 코드 또는 JSON 실행 자동화
- 커밋 또는 푸시 자동화

이 항목들은 이후 Phase에서 다룬다.

## 완료 기준

Handoff 기반 작업은 다음 조건을 만족해야 완료로 볼 수 있다.

- 필요한 승인을 받았다.
- 실행이 승인 범위 안에 머물렀다.
- 리뷰 요구가 처리되었거나 명시적으로 보류되었다.
- 검증을 수행했거나 명시적으로 보류되었다.
- 결과와 남은 위험을 기록했다.
- 의미 있는 작업이면 DevLog가 존재한다.
- Git 작업은 사용자가 요청한 경우에만 수행했다.
