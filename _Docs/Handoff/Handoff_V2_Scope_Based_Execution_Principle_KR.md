# Handoff v2 범위 기반 실행 승인 원칙

## 목적

이 문서는 AI Role Handoff System v2에서 가져갈 구현 승인 기준을 기록한다.

기준은 다음이다.

```text
승인 트리거는 소스 코드 수정 자체가 아니라, 승인된 업무 범위를 벗어났는지 여부다.
```

## 핵심 규칙

사용자가 Handoff Packet, DeveloperPlan, work order, 또는 그에 준하는 실행 범위를 승인했다면, 받는 역할은 그 범위를 완료하기 위해 필요한 일반적인 소스 코드 수정과 스키마 변경이 아닌 데이터 수정을 진행할 수 있다.

구현에 소스 코드 수정이 필요하다는 이유만으로 다시 승인을 요청하지 않는다.

소스 코드 수정은 Developer 작업의 정상적인 일부다. 승인 범위에 포함되어 있고 schema, save/load, persistent data 의미를 바꾸지 않는 일반 데이터 수정도 정상적인 실행에 포함된다.

## 승인이 의미하는 것

승인된 실행 범위는 최소한 다음을 설명해야 한다.

- 게임, 워크플로우, 데이터, 저장소 관점에서 무엇을 바꿀 것인가
- 어떤 역할이 실행할 것인가
- 어떤 파일, 시스템, 영역이 작업 대상인가
- 어떤 파일, 시스템, 영역은 범위 밖인가
- 결과를 어떻게 검증할 것인가

이 범위가 승인되면 Developer는 그 안에서 작업한다.

## 다시 멈춰야 하는 때

역할은 승인된 경계를 벗어나야 할 때만 다시 멈추고 승인을 요청한다.

예:

- 승인된 범위 밖의 파일, 시스템, 동작이 필요해진다.
- 승인되지 않은 JSON schema, save/load, migration, persistent data 의미 변경이 필요하다.
- 승인된 계획에 없던 구조적 리팩터링이 필요하다.
- 승인 대상 밖의 공통 아키텍처나 lifecycle 규칙에 영향을 준다.
- 기획 목표가 승인된 내용과 실질적으로 달라지거나 애매해진다.
- build setting, commit, push, release, deployment, workflow rule 변경이 필요하다.

## Supervisor 해석

Supervisor와 향후 Role Worker 자동화는 `소스 코드가 바뀌었다`는 사실만으로 승인 위반으로 보면 안 된다.

대신 그 소스 코드 변경이 승인된 실행 범위 안에 있는지를 봐야 한다.

찾아야 할 문제는 이것이다.

```text
구현이 승인된 범위 밖으로 나간 것으로 보임
```

이지, 이것이 아니다.

```text
구현이 소스 코드를 수정함
```

## 기존 v1 문서와의 관계

Handoff v1은 보수적인 문서 기반 운영 계층이다.

이 v2 원칙은 다음 운영 목표를 분명히 한다. 정상적인 Developer 실행이 파일 하나하나 허락받는 흐름이 되어서는 안 된다.

기존 승인 대기 문서는 승인된 실행 범위가 없거나, 역할이 승인 범위 밖으로 나가야 할 때 계속 적용된다.

## Human Director 의도

사용자는 전체 시스템의 감독관이지, 모든 코드 수정마다 허락을 내리는 개별 팀장이 아니다.

승인된 작업 안에서 생기는 실수는 사전 미세 승인으로 막는 것이 아니라 리뷰, 검증, 수정, 롤백으로 처리한다.
