Handoff System User Guide

역할별 AI 채팅들이 같은 저장소에서 일을 주고받는 방법

AI Role Handoff System은 Planner, Developer, Artist, Reviewer, QA 같은 역할 채팅이 기획서, 구현 요청, 리소스 안내, 승인 요청, 결과 보고를 같은 저장소 안에서 주고받기 위한 문서 기반 운영 체계다.

가장 중요한 원칙 Handoff는 AIWorkflow를 대체하지 않는다. Handoff는 업무 큐와 전달 인터페이스이고, AIWorkflow는 승인, 위험도, 검증, 완료 판정의 안전 엔진이다.

핵심 모델

Handoff
  • 역할 간 업무 큐
  • 전달 인터페이스
  • Dashboard와 Queue로 상태 표시
→
AIWorkflow
  • 승인 기준
  • 위험도와 범위 판단
  • 검증과 완료 판정 규칙
DevLog
  • 조사와 수정 이력
  • 검증 결과
  • 남은 리스크와 다음 작업
→
Git
  • 실제 파일 변경 이력
  • 커밋과 푸시 기록
  • 되돌릴 수 있는 변경 단위
관계: Handoff는 일을 전달하고 보여준다. AIWorkflow는 그 일이 어떤 승인/검증 규칙을 따라야 하는지 결정한다. DevLog는 완료된 일의 맥락을 남기고, Git은 실제 저장소 변경을 기록한다.

기획 승인과 실행 승인은 다르다

구분 의미
기획 승인 이 방향의 기능, 콘텐츠, 디자인, 요구사항으로 간다는 것을 사용자가 받아들인 상태
실행 승인 특정 역할이 특정 파일, 데이터, 런타임 동작, 도구, Git 상태를 바꿔도 된다고 사용자가 허용한 상태
Ready는 실행 승인이 아니다 Handoff 항목이 Ready라는 뜻은 받는 역할이 확인할 준비가 되었다는 뜻이다. 실행 범위가 승인되기 전까지는 코드, JSON, 런타임, 빌드, Git 변경을 시작하지 않는다.
승인은 코드 수정 여부가 아니라 범위 기준이다 Packet, DeveloperPlan, work order 등으로 실행 범위가 승인되면 Developer는 그 범위 안의 일반적인 코드와 스키마 변경이 아닌 데이터를 수정한다. 다시 승인이 필요한 때는 작업이 승인된 범위를 벗어날 때다.

기본 사용 흐름

1. 기획 논의 사용자와 Planner가 목표, 범위, 제외 항목을 맞춘다.
→
2. 기획 방향 승인 무엇을 할지 확정한다. 이 승인만으로 무제한 변경이 허용되지는 않는다.
→
3. Packet 작성 Planner가 Packets/<handoff-id>/에 brief, request, manifest를 남긴다.
4. Supervisor 정리 Dashboard, Queues, Violations를 갱신해 현재 일감을 보이게 한다.
→
5. 역할별 수거 Developer, Artist, Reviewer, QA가 자기 Queue와 Packet을 확인한다.
→
6. 계획과 범위 확인 받는 역할은 먼저 작업 계획과 승인된 실행 범위를 확인한다.
7A. 범위 안 작업 승인된 목표와 경계 안의 일반 구현, 문서, 비스키마 데이터 작업은 진행한다.
7B. 범위 밖 작업 목표, 파일, schema, save/load, lifecycle, build setting이 벗어나면 WaitingUserApproval로 멈춘다.
8. 결과 기록 Results, CompletionNotice, DevLog에 실제 변경과 검증 결과를 남긴다.
→
9. 리뷰와 QA 리뷰 요청, QA 요청, 사람 QA 결과를 Packet에 연결한다.
→
10. 완료 판단 Done 처리 후 필요한 경우 사용자가 커밋과 푸시를 결정한다.

Handoff Packet

여러 문서, 여러 역할, 승인 요청, 결과 문서가 필요한 작업은 Packet으로 만든다. Packet은 manifest.yaml을 중심으로 계획, 요청, 결과, 완료 노티를 묶는다. 

_Docs/Handoff/Packets/
  HANDOFF-YYYYMMDD-###-short-slug/
    manifest.yaml
    PlanningBrief.md
    ImplementationRequest.md
    ArtRequest.md
    ReviewRequest.md
    QARequest.md
    CompletionNotice.md
    ResourceNotes/
      ResourceNotes.md
    Results/
      DeveloperPlan.md
      DeveloperResult.md
      ReviewResult.md
      QAResult.md

상태는 두 개로 나눈다

필드 의미
delivery_status 역할 간 전달 흐름에서의 상태
execution_status 받는 역할의 계획, 승인, 실행, 리뷰, 완료 상태
권장 시작점 새 Packet은 _Docs/Handoff/Packets/_Manifest_Template.yaml을 복사해서 시작한다.

역할별 루틴

역할 주요 책임 문서
Planner 승인된 기획 방향을 Packet으로 만든다. Role_Routines/Planner_Routine.md
Developer 승인된 실행 범위 안에서 구현하고, 범위 밖 변경은 승인 요청 후 멈춘다. Role_Routines/Developer_Routine.md
Artist 리소스 요청, 위치, 사용 조건, 전달 내용을 정리한다. Role_Routines/Artist_Routine.md
Reviewer 범위, 승인, 검증, 아키텍처 위험을 리뷰한다. Role_Routines/Reviewer_Routine.md
QA 완료 기준에 맞춰 통과/실패/막힘/미실행을 분리해 기록한다. Role_Routines/QA_Routine.md

승인 대기

높은 위험 작업은 마음속으로만 멈추면 안 된다. Packet과 00_Index.md에 사용자가 찾을 수 있는 승인 대기 상태로 표시해야 한다.

승인 요청서에 꼭 들어갈 것

  • 무엇을 바꾸려는가
  • 플레이어, 사용자, 게임, 워크플로우 관점에서 어떤 변화가 생기는가
  • 어떤 코드/데이터 개념이 영향을 받는가
  • 예상 변경 파일
  • 하지 않을 것
  • 위험과 검증 계획
  • 사용자에게 필요한 결정
잘못된 승인 요청 "런타임 동작 변경이라 승인 필요합니다."
좋은 승인 요청 "몬스터 이동 시스템에 Flying 패턴을 추가해 특정 몬스터가 지상 이동 대신 공중 경로를 사용하게 하려 합니다. Enemy 이동 로직과 Enemy.json 데이터에 영향을 줍니다. 아래 파일 범위와 검증 계획대로 진행해도 될까요?"

범위 기반 승인

v2 기준은 코드 수정 자체가 아니라 승인된 업무 범위를 기준으로 판단한다. 실행 범위가 승인된 뒤에는 Developer가 그 안에서 필요한 일반적인 코드와 스키마 변경이 아닌 데이터를 수정한다.

상황 처리
승인된 Packet 또는 DeveloperPlan 범위 안의 구현 별도 파일별 승인 없이 진행
승인 범위 밖 파일, 시스템, 동작이 필요함 WaitingUserApproval로 멈추고 범위 확장 요청
승인되지 않은 schema, save/load, lifecycle, build, Git 변경 별도 승인 요청

읽기 전용 스캔

Phase 5의 스캐너는 보고만 한다. 파일을 만들거나 수정하지 않고, claim하지 않고, 상태를 바꾸지 않는다.

스캔 모드 확인 내용
전체 큐 현재 Packet과 active handoff 목록
역할별 큐 Developer, Artist, Reviewer, QA 등 특정 역할 대상 작업
승인 대기 execution_status: WaitingUserApproval 항목
정합성 manifest/index 불일치, 누락 문서, 숨겨진 승인 대기

Handoff Supervisor

Supervisor는 Packet manifest를 읽어서 사람이 볼 수 있는 Dashboard, 역할별 Queue, Open Violations를 만든다. 역할 채팅의 숨은 기억을 믿는 대신 저장소에 남은 파일 상태를 기준으로 업무, 승인 대기, 구조 문제를 드러내는 계층이다. 

tools\aiworkflow\handoff_supervisor.bat status
tools\aiworkflow\handoff_supervisor.bat scan --role Developer
tools\aiworkflow\handoff_supervisor.bat status --json
tools\aiworkflow\handoff_supervisor.bat write-docs
tools\aiworkflow\handoff_supervisor.bat write-docs --execute
write-docs는 기본적으로 쓰지 않는다 write-docs만 실행하면 생성 예정 파일만 보여준다. 실제로 Dashboard.md, Queues/, Violations/Open.md를 갱신하려면 --execute가 필요하다.
Supervisor가 하지 않는 일 Supervisor는 게임 소스, 게임플레이 JSON, 에셋, 빌드 설정, approval evidence, commit, push를 바꾸지 않는다. 다른 역할 채팅을 자동으로 깨우거나 제어하지도 않는다.

문서/상태 갱신 경계

Phase 6은 문서-only 상태 갱신의 경계를 정의한다. 허용 가능한 것은 Handoff 문서 내부의 제한적 갱신뿐이다.

허용될 수 있는 것 여전히 금지되는 것
Index 동기화, claim 메타데이터, 계획/결과 문서, 승인 대기 기록, 리뷰/QA 라우팅, 완료/보관 기록 승인 범위 밖 코드/데이터/런타임 변경, JSON 스키마 변경, 빌드/테스트 실행, 자동 승인, 검증 없는 Done, 커밋/푸시

운영 체크리스트

실제 운영 중에는 Dashboard.md를 먼저 보고, 문제가 있으면 Violations/Open.md를 확인한다. 역할별 작업은 Queues/<Role>.md에서 확인하고, 승인 대기 항목은 연결된 Packet의 요청 문서를 읽고 결정한다. 

tools\aiworkflow\handoff_supervisor.bat status
상황 해야 할 일
Waiting User Approval 요청 문서를 열고 승인, 거절, 범위 수정 중 하나를 결정한다.
Consistency Issues > 0 새 작업을 진행하기 전에 Violations/Open.md를 먼저 해결한다.
Scope Status: Approved 승인된 실행 범위 안에서 역할이 구현을 진행할 수 있다.
Scope Drift Issues 변경 파일이 승인 범위 밖인지 확인하고, 필요하면 범위 확장을 승인한다.
Ready Work 역할은 읽고 계획할 수 있다. 구현은 별도 실행 범위가 승인된 뒤 진행한다.
CompletionNotice 검증 기록과 남은 위험을 보고 commit/push 여부를 판단한다.

Phase 상태

Phase 1 완료: 운영 원칙
Phase 2 완료: Packet / manifest 구조
Phase 3 완료: 역할별 루틴
Phase 4 완료: 수동 파일럿 Packet
Phase 5 완료: 읽기 전용 스캐너 설계
Phase 6 완료: 문서/상태 갱신 경계
Phase 7A 완료: Handoff Supervisor MVP. Packet을 읽고 Dashboard, 역할별 Queue, Open Violations를 생성한다.
Phase 7B 완료: Skill Shortcut Key Label Mapping Packet으로 Planner → Developer 전달, Ready 검출, WaitingUserApproval 승인 대기 흐름을 검증했다.
Phase 7C 완료: 사용자가 DeveloperPlan을 승인한 뒤 제한 구현, Debug x64 빌드 검증, 사용자 런타임 QA 확인까지 완료했다. Packet은 Done 상태다.
Phase 7D 완료: Phase 7A~7C 결과 커밋을 origin/main에 push했다.
Phase 8A 완료: Dashboard와 역할별 Queue가 Ready, Review Requested, QA Requested, Blocked 같은 운영 상태를 별도 섹션으로 보여주도록 개선했다.
Phase 8B 완료: Supervisor가 Packet manifest와 00_Index.md의 정합성을 읽기 전용으로 점검하고, 불일치를 Violations/Open.md에 표시하도록 개선했다.
Phase 9A 완료: 실제 반복 자동화를 만들기 전에 Supervisor 자동화 모드, 허용 범위, 금지 행동, 첫 자동화 프롬프트를 운영 문서로 고정했다.
Phase 9B 완료: playground-handoff-supervisor Codex recurring automation을 60분 주기, 파일 갱신 허용, ACTIVE 상태로 생성했다.
Phase 9C 완료: 첫 Supervisor 자동화 실행을 검증했다. 생성 Handoff 표면만 갱신됐고, Handoff 정합성 문제는 0건이었다.
Phase 10A 완료: 역할 채팅 또는 미래의 역할 직원 자동화가 Queue를 수거하기 전에 따라야 할 Intake 계약과 Intake Decision 템플릿을 추가했다.
Phase 10B 완료: 역할 채팅이 실제 작업 전에 Handoff 계약을 적용할 준비가 되었는지 확인하는 Contract Check, Blind Scenario, Run Report 하네스를 추가했다.
Phase 10C 완료: Developer 역할 기준으로 Contract Check와 Blind Scenario 파일럿을 기록했다. 독립 역할 채팅 테스트는 아직 남아 있다.
Phase 11A 완료: 미래 역할 직원 자동화 전에 낮은 위험 후보 작업과 반드시 승인 대기해야 하는 작업의 경계를 정의했다.
Phase 11B 완료: 실제 완료 Packet을 근거로 Developer 역할이 Queue를 확인하고 low-risk 문서 보고서를 작성하는 파일럿을 완료했다.
Phase 11C 완료: QA 역할도 같은 문서-only 경계를 반복 적용할 수 있는지 확인했다.
Phase 12A 완료: 실제 자동화를 만들기 전에 단일 low-risk 역할 직원 자동화의 입력, 출력, 중지 규칙, 반복 실행 안전 규칙을 설계했다.
Phase 12B 완료: playground-handoff-role-worker-low-risk 자동화를 60분 주기, PAUSED 상태, run report only 범위로 생성했다.
Phase 12C 완료: Role Worker 자동화를 일시 활성화해 첫 실행을 확인했고, run report 1개만 작성한 뒤 다시 PAUSED로 돌렸다.
Phase 13A 완료: 승인 대기 항목을 사용자가 판단할 수 있도록 승인 요청 문서의 결정 선택지와 응답 문장 기준을 강화했다.
Phase 13B 완료: 실제 승인 대기 Packet을 만들어 Dashboard, Developer Queue, Index에서 승인 요청 문서까지 이어지는 흐름을 검증했다.
Phase 13C 완료: Supervisor가 사용자 승인 대기 Packet의 승인 요청 문서에서 필수 섹션과 승인/거절/범위 수정 선택지 누락을 감지하도록 했다.
Phase 14 완료: Dashboard, Violations, Queue, Packet 문서를 어떤 순서로 보고 무엇을 결정해야 하는지 운영 체크리스트로 고정했다.
Phase 15 완료: Handoff v1 운영 준비 상태를 감사했고, 문서 기반 운영은 통과, 완전 자율 역할 실행은 보류로 판정했다.
Phase 16 완료: Handoff v1 최종 범위, 범위 밖 항목, 일상 요청 문장, 유지보수 정책, v2 후보를 고정했다.
Phase 17 완료: approved_execution_scope와 승인 범위 경로 필드를 manifest 계약으로 추가했다.
Phase 18 완료: Supervisor와 생성 Dashboard/Queue가 Scope Status, 승인 범위 수, 누락 범위 수를 표시한다.
Phase 19 완료: Developer와 Role Worker 루틴을 코드 수정 승인 대기가 아니라 범위 밖 변경 승인 대기로 전환했다.
Phase 20 완료: Supervisor가 Git 변경 파일 경로를 active 승인 Packet의 허용 범위와 비교해 scope drift 의심 항목을 표시한다.
