# 스킬 시스템 구조 검증 보고서

작성일: 2026-04-17  
기준 문서: `스킬 시스템 재정비 기획서 v2 (확정본)`

## 1. 검증 기준선

이번 검증은 아래 책임 구분을 기준으로 수행했다.

- `SkillData`: 스킬 정의와 파라미터. 현재 기준선은 `SkillJsonInfo`와 `Skill.json`.
- `SkillRuntime`: 쿨다운, 시전 상태, 입력 차단, 시전 완료 시점 관리.
- `Execution`: 실제 발동 후 생성되는 투사체/버프/디버프/공전 객체와 판정 처리.

검증 대상 범위는 아래 파일군을 포함한다.

- `Project/Gameplay/Common/CommonGamePlayType.h`
- `Project/Gameplay/GamePlaySystems/SkillManager.*`
- `Project/Gameplay/GamePlaySystems/Skills/*`
- `Project/Gameplay/Components/Movement.*`
- `Project/Gameplay/Components/Status.*`
- `Project/Gameplay/Components/Combat.cpp`
- `Project/Gameplay/Actors/Stage/StagePlayer.cpp`
- `Project/Gameplay/Actors/Stage/UnitBase.cpp`
- `Project/Gameplay/Common/HitContext.h`
- 비교 기준용 공통 피격 구현: `Actors/Projectile/Bullet.cpp`, `Actors/Stage/ContactAttackAbility.cpp`

판정은 다음 세 단계로 표기했다.

- `일치`: 기획 의도와 현재 구현이 구조적으로 맞는다.
- `부분 일치`: 현재 동작은 비슷하지만, 구조적으로 보장이 없거나 우연한 동작에 의존한다.
- `불일치`: 기획 의도와 구현이 직접 충돌한다.

## 3. 구조 문제 목록

### [P0] 공통 피해/넉백 시스템 우회

- 분류: `공통 시스템 우회`
- 영향 범위: `실행 오브젝트`, `피해/상태/넉백 공통계층`
- 근거:
  - 공통 경로 정의: `HitContext.h:10-26`
  - 공통 경로 사용 예: `Bullet.cpp:70-84`, `ContactAttackAbility.cpp:56-63`, `UnitBase.cpp:40-60`
  - 우회 구현: `DustGustObject.cpp:60-63`, `AtmosphericCorrosionObject.cpp:109-112`, `LintSatelliteObject.cpp:138-142`
- 문제:
  - 세 스킬이 `ApplyHit()` 대신 `GetDamage()`를 직접 호출한다.
  - 넉백, 카메라 반응, dash attack 여부, 향후 저항/면역/피격 메타가 모두 스킬별로 누락되거나 따로 구현돼야 한다.
  - 현재 보풀 위성의 넉백 누락이 이 구조 문제의 직접 결과다.

### [P0] 비즉시 시전 런타임 부재

- 분류: `데이터 누락`, `책임 혼합`
- 영향 범위: `스킬 데이터`, `시전 상태`, `스킬 생성`
- 근거:
  - 데이터 정의: `CommonGamePlayType.h:527-589`
  - 런타임 현재 형태: `SkillBase.h:10-33`
  - 즉시 실행 진입: `SkillManager.cpp:73-83`, `StagePlayer.cpp:103-112`
- 문제:
  - 캐스팅 시간, 캐스팅 상태, 입력 차단 정책, 관성 유지 정책이 구조적으로 존재하지 않는다.
  - 따라서 먼지 돌풍과 보풀 위성을 기획대로 “비즉시 시전”으로 만들 수 없다.

  - 보풀 위성과 먼지 돌풍이 모두 “히트 판정 + 피해 적용”을 갖지만 공통 규약을 공유하지 않는다.

### [P1] 부식이 확장형 디버프가 아니라 고정형 장판 도트에 가까움

- 영향 범위: `실행 오브젝트`

### [P2] 먼지 돌풍의 1회 타격이 명시적 정책이 아님

- 분류: `확장성 저해`

### [P2] Invincible과 Knockback immunity가 구조적으로 분리되지 않음

- 분류: `상태 정의 위반`
- 영향 범위: `Status`, `Movement`, `피해/상태/넉백 공통계층`

- 문제:
  - 현재 무적은 피해 무시 플래그 하나이며, 넉백 면역은 그 부수 효과로만 성립한다.
  - 기획의 상태 정의를 그대로 표현하는 모델이 아니므로, 향후 피격 종류가 늘면 쉽게 무너진다.

## 4. 구조 기반 수정안

수정안은 “값만 바꾸는 임시 보정”이 아니라, 기획서의 분리 원칙을 만족하도록 계층을 다시 세우는 방향으로 제안한다.

### 4-1. 공통 기반 도입

- 목표:
  - `SkillData`, `SkillRuntime`, `Execution`을 명시적으로 분리한다.
  - `if/switch` 없이 스킬 정의가 실행 전략을 선택하도록 만든다.

- 제안 구조:
  - `SkillData`
    - `SkillJsonInfo` 또는 그로부터 로드되는 별도 `SkillDefinition`에 아래 정책을 명시한다.
    - `cast_mode` (`Instant`, `Timed`)
    - `execution_kind` (`Projectile`, `Debuff`, `Buff`, `Orbiting`)
    - `hit_policy` (`SinglePerTargetLifetime`, `PerTargetInterval`, `EnterOnlyCapture` 등)
    - `state_policy` (`Root`, `Invincible`, `KnockbackImmune`, `MoveInputLock` 등)
  - `SkillRuntime`
    - 쿨다운과 함께 `Idle / Casting / Cooldown` 상태를 소유한다.
    - non-instant 스킬의 cast timer, owner, aim direction을 보관한다.
  - `Execution`
    - `ISkillExecution` 인터페이스를 두고, `ProjectileExecution`, `DebuffExecution`, `BuffExecution`, `OrbitingExecution`으로 분리한다.
    - 스킬별 클래스는 “어떤 실행 전략을 쓸지”만 결정하고, 판정 규약은 실행 타입 계층이 가진다.

- 영향 파일군:
  - `CommonGamePlayType.h`
  - `GamePlaySystems/Json/SkillJsonDataManager.*`
  - `GamePlaySystems/SkillManager.*`
  - `GamePlaySystems/Skills/*`

- 선행 조건:
  - 스킬 정의에 들어갈 enum과 정책 구조를 먼저 확정해야 한다.

- 리스크:
  - 데이터 포맷 변경 시 기존 `Skill.json` 마이그레이션이 필요하다.

### 4-2. 공통 피해/상태/넉백 규약 통일

- 목표:
  - 모든 공격이 `HitContext -> ApplyHit -> ApplyHitReaction` 공통 경로를 통과하도록 만든다.
  - 상태 효과와 넉백 면역이 “데미지 0의 부수 효과”가 아니라 명시적 정책으로 작동하게 만든다.

- 제안 구조:
  - 모든 스킬 히트는 `HitContext`를 생성해 `ApplyHit()`를 호출한다.
  - `UnitBase::ApplyHitReaction()` 전에 상태 면역을 검사하는 전용 정책 지점을 둔다.
  - `Invincible`은 최소한 `damage immune + knockback immune`를 함께 표현하는 상태로 승격한다.
  - `Root`는 `Movement::SetEnable(false)`가 아니라 “자발 이동만 차단”하는 제어 플래그로 구현한다.
  - 현재 `Movement::SetAllowNormalMove(false)`는 입력 이동만 끄고 관성/넉백은 유지하므로, Root/캐스팅 차단의 기반 도구로 재사용할 수 있다.
  - 단, 여러 시스템이 동시에 이동 차단을 걸 수 있으므로 단일 bool이 아니라 reason flag 또는 reference-counted lock으로 바꿔야 한다.

- 영향 파일군:
  - `Common/HitContext.h`
  - `Actors/Stage/UnitBase.*`
  - `Components/Status.*`
  - `Components/Movement.*`
  - 각 스킬 오브젝트 파일

- 선행 조건:
  - 상태 정책 테이블과 이동 차단 reason 모델을 먼저 확정해야 한다.

- 리스크:
  - 플레이어 공격, 적 공격, 스킬 오브젝트가 모두 같은 경로로 합쳐지므로 회귀 범위가 넓다.

### 4-3. 4개 스킬 마이그레이션

#### 먼지 돌풍

- `ProjectileExecution` 기반으로 이전한다.
- `hit_policy = SinglePerTargetLifetime`를 명시한다.
- 타깃별 hit set 또는 reusable hit gate를 런타임에 둔다.
- 데미지는 `HitContext`를 사용한다.

#### 부식

- `DebuffExecution` 기반으로 이전한다.
- 0.5초 확장 판정과 3초 디버프 지속을 분리한다.
- 대상 확정은 `collision enter`만 사용한다.
- 즉시 피해는 제거하고, 디버프 tick만 피해를 발생시킨다.
- Root는 `allow_normal_move` 차단 계층을 통해 “이동만 차단”으로 바꾼다.

#### 다크사이트

- `BuffExecution` 기반으로 이전한다.
- `Invincible`, `KnockbackImmune`, `MoveSpeedMultiplier`를 명시적 버프 정책으로 적용한다.
- “현재 속도 = 최대속도”는 정지 상태 처리 방식까지 포함해 정책을 고정해야 한다.
  - 권장: 시전 시 바라보는 방향 또는 현재 입력 방향이 있으면 즉시 최고속도로 세팅하고, 없으면 최소한 현재 속도를 0으로 두되 기획 문구를 조정할지 별도 확인이 필요하다.

#### 보풀 위성

- `OrbitingExecution` 기반으로 이전한다.
- 공전 계산은 유지하되, 히트 처리는 `PerTargetInterval` 게이트와 `HitContext` 공통 경로로 바꾼다.
- 넉백은 기존 `ApplyHitReaction()` 체계와 연결한다.

- 영향 파일군:
  - `GamePlaySystems/Skills/*`
  - 필요 시 스킬별 실행 하위 디렉터리 신설

- 리스크:
  - 스킬별 비주얼은 유지하면서 판정만 교체해야 하므로, 오브젝트 수명과 시각 연출이 분리되지 않으면 충돌 가능성이 있다.

### 4-4. 스킬별 분기 제거

- 목표:
  - `SkillManager`가 더 이상 ID 기반 `switch`를 가지지 않도록 만든다.

- 제안 구조:
  - 등록 기반 팩토리 또는 `execution_kind -> execution factory` 매핑을 둔다.
  - 장착 슬롯은 `SkillRuntime`만 소유하고, 실제 실행 객체는 등록된 execution factory가 생성한다.
  - 스킬 추가 시 수정 지점은 “등록 테이블” 또는 “데이터” 하나만 남도록 정리한다.

- 영향 파일군:
  - `SkillManager.*`
  - 스킬 등록 초기화 코드

- 리스크:
  - 초기화 순서와 singleton 의존성이 엮일 수 있으므로, 등록 시점을 명확히 해야 한다.

### 4-5. 회귀 검증

- 구조 검증
  - `SkillData / Runtime / Execution`이 실제 클래스 계층으로 분리되었는지 확인
  - `SkillManager`에서 ID `switch`가 제거되었는지 확인
  - `Projectile / Buff / Debuff / Orbiting`가 공통 실행 계층으로 분리되었는지 확인

- 스킬 기능 검증
  - 먼지 돌풍이 관통하며, 동일 대상 lifetime 동안 1회만 타격하는지 확인
  - 부식이 0.5초 동안 확장한 뒤 enter 대상만 디버프에 등록하는지 확인
  - 부식 tick이 즉시 피해 없이 1초 간격 3회로 들어가는지 확인
  - Root 상태에서 자발 이동만 막히고 넉백은 유지되는지 확인
  - 다크사이트가 피해와 넉백을 모두 무효화하는지 확인
  - 다크사이트가 이동속도 1.5배와 즉시 속도 보정을 적용하는지 확인
  - 보풀 위성이 공전하면서 대상별 0.5초 hit interval과 넉백을 함께 적용하는지 확인
  - 비즉시 시전 스킬 사용 중 이동 입력이 차단되고, 기존 관성은 유지되는지 확인

## 5. 결론

현재 코드는 “스킬별 오브젝트를 빠르게 붙여 넣은 1차 구현”으로는 동작하지만, 기획서가 요구한 구조에는 도달하지 못했다.

핵심 원인은 세 가지다.

- 시전 런타임이 없어서 비즉시 시전을 표현할 수 없다.
- 공통 히트/넉백 규약을 일부 스킬이 우회한다.
- 상태가 정책이 아니라 개별 구현 세부사항으로 흩어져 있다.

따라서 수정은 개별 스킬 조건문을 덧붙이는 방식이 아니라, 반드시 아래 순서로 진행하는 것이 안전하다.

1. 공통 데이터/런타임/실행 계층 도입
2. 공통 히트/상태 규약 통일
3. 4개 스킬 마이그레이션
4. `SkillManager` 분기 제거
5. 회귀 검증
