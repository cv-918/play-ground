# Fix Log - 2026-04-18

## 작업 목적
씬 전환 및 오브젝트 정리 과정에서 이미 삭제된 객체를 다시 참조해 크래시가 발생하는 문제를 줄이기 위해, `Scene`, `ObjectManager`, `UIManager`, `GameObject`, `UI`, `Collider` 전반의 라이프사이클 흐름을 점검하고 보강.

특히 아래 상황을 주요 타겟으로 삼았다.
- 씬 전환 시 기존 씬 삭제 과정에서 액터와 UI가 한꺼번에 정리되는 경우
- 액터 삭제 중 `Collider` 소멸자 또는 충돌 정리 로직이 이미 사라진 상대 collider/object를 다시 만지는 경우
- 씬/시스템이 raw pointer로 캐시한 대상을 나중 프레임에 다시 사용하는 경우

---

## 문제 인식 요약

### 1. 소유권과 참조의 분리
- 실제 소유권은 `ObjectManager`/`UIManager`가 가지는데,
- `Scene`, `RunState`, `Skill`, `Projectile`, `Widget`, 일부 컴포넌트가 raw pointer를 따로 캐시하고 있었다.

이 구조 자체가 반드시 잘못된 것은 아니지만, 파괴 시점 통지가 없으면 다음과 같은 문제가 생긴다.
- 이미 파괴된 오브젝트를 다음 프레임에 업데이트/렌더/뷰 전환 로직에서 다시 참조
- 씬 종료 중 삭제 순서에 따라 `OnDestroy()`에서 다른 시스템이 이미 정리된 상태를 가정하지 못함
- 충돌 정리 시 `collided_colliders_`에 남은 상대 collider를 따라가다 dangling pointer 접근

### 2. 파괴 시점에 게임플레이 부작용이 섞여 있었음
- 일부 로직은 "죽음 처리"와 "실제 delete 시점"이 섞여 있었다.
- 예: 플레이어/적 사망 보상, 상태 전이, 결과 처리 등이 `OnDestroy()` 또는 파괴 직전 흐름과 가까운 곳에 놓여 있어 정리 순서에 민감했다.

### 3. 씬 종료와 개별 삭제를 같은 방식으로 처리하고 있었음
- "오브젝트 하나가 정상적으로 제거되는 경우"와
- "씬 전체가 내려가면서 한 번에 정리되는 경우"는 성격이 다르다.
- 후자의 경우 다른 시스템도 같이 종료되므로, 일반 삭제와 같은 side effect를 그대로 타면 참조 꼬임이 더 쉽게 발생한다.

## 핵심 보강 내용

### 1. `IDestroyable` 파괴 콜백 체계 추가
- `Project/Core/Interface/Interfaces.h`

추가 내용:
- `AddDestructionCallback`
- `RemoveDestructionCallback`
- `OnDestroy()`
- `OnSceneShutdown()`

의도:
- raw pointer를 캐시하는 쪽이 대상의 파괴를 통지받고 즉시 포인터를 비울 수 있게 함
- 개별 삭제와 씬 종료를 구분해, 씬 종료 시 불필요한 gameplay side effect를 줄일 수 있게 함

### 2. 씬 종료 경로 분리
- `Project/Gameplay/GamePlaySystems/ObjectManager.h/.cpp`
- `Project/Gameplay/GamePlaySystems/UIManager.h/.cpp`
- `Project/Gameplay/Scenes/Scene.cpp`

적용 내용:
- `ObjectManager::_DestroyGameObject(..., _scene_shutdown)`
- `UIManager::_DestroyUI(..., _scene_shutdown)`
- 일반 `CleanUp()`는 `OnDestroy()`

의도:
- 씬 전체 종료 시 UI가 먼저 정리되어도, UI가 추적하던 게임오브젝트 참조를 안전하게 끊을 수 있게 함
- 게임오브젝트 삭제가 후행되더라도 dangling reference 가능성을 낮춤

### 3. 충돌 시스템 정리 보강

## 리뷰

### 이번 작업에서 좋았던 점
1. 파괴 통지를 공용 인터페이스(`IDestroyable`) 차원으로 끌어올린 점
2. 씬 종료와 개별 삭제를 분리해 side effect를 제어할 수 있게 만든 점
3. "죽음 처리"와 "실제 메모리 해제"를 분리해 gameplay/state 전이를 더 예측 가능하게 만든 점
4. collider 정리를 시스템 차원에서 먼저 수행하도록 바꿔, 최초 문제 제기와 직접 맞닿은 위험을 낮춘 점
5. x64 빌드 불안정성까지 같이 정리해 이후 검증 루프가 수월해진 점

### 아직 남아 있는 리스크 / 후속 후보
1. 전체 경고 18개는 여전히 남아 있으며, 대부분 수치 변환 관련 경고다.
2. `SceneManager::Update()` / `LateUpdate()`는 현재 scene 반환값을 적극적으로 사용하지 않는다.
3. 런타임 실기 테스트는 아직 충분히 하지 못했다. 특히 아래 시나리오 재현 확인이 필요하다.
   - `InGame -> Pause -> Exit -> OutGame`
   - 플레이어 사망 직후 `ResultView` 노출
   - `OutGame`에서 뷰 전환 중 씬 전환
4. raw pointer 캐시를 줄였지만, 장기적으로는 소유권 모델을 더 명확히 정리할 여지가 있다.

## 빠른 체크리스트
1. `InGame`에서 `ESC`로 `Pause` 진입 후 바로 종료해도 크래시가 없는지
2. 적/플레이어가 죽는 프레임에 collider 정리 후 후속 `LateUpdate`에서 접근 오류가 없는지
3. `OutGame` 뷰를 여러 번 열고 닫은 뒤 `InGame`으로 전환해도 `current_view_` 관련 오류가 없는지
4. `HpBar`, `Dust`, `Bullet`, skill 실행 오브젝트가 추적 대상 파괴 후 정상적으로 무반응/null-safe 동작하는지
5. `Debug | x64`, `Release | x64`가 계속 재현 가능하게 빌드되는지

## 한 줄 결론
이번 작업은 "삭제 순서에 운 좋게 기대던 구조"를 "파괴 통지와 사전 정리를 전제로 한 구조"로 옮기는 첫 정리였다. 아직 후속 검증은 필요하지만, 씬 전환/사망 처리/충돌 정리에서 가장 위험한 dangling pointer 구간은 상당 부분 줄어든 상태다.
